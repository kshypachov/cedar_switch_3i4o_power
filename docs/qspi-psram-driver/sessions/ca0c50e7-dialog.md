## Как это выглядит на практике

Вместо `chip-variant = "IS66WVS4M8BLL"` и записи в `chip_table[]` появляется файл `dts/bindings/mtd/issi,is66wvs4m8bll.yaml`:

```yaml

include: qspi-psram-mspi.yaml

properties:
  size:
    default: 33554432        # 32 Mbit
  read-command:
    default: 0xEB            # QPI fast read
  write-command:
    default: 0x38
  command-length:
    default: "INSTR_1_BYTE"
  address-length:
    default: "ADDR_3_BYTE"

    default: 6
  ce-break-config:
    default: [1024, 4]       # page 1 KB, tCEM 4 us
```

А узел пользователя сводится к:

```dts
psram0: psram@0 {
    compatible = "issi,is66wvs4m8bll";
```

## Коротко

Механически автодетект почти весь уже есть в драйвере — force SPI → reset → Read ID работают. Добавить нужно четыре вещи: расширенное чтение ID (сейчас читаются 3 байта, нужен полный EID), таблицу «ID → параметры» в C, режим «auto» в биндинге и — самое неприятное — способ донести определённый в рантайме размер до memory-mapped окна контроллера. Последний пункт на STM32 сейчас невозможен без правки драйвера контроллера, и это главный подводный камень.

## Что чип умеет сообщить о себе

У QPI PSRAM нет аналога SFDP, как у NOR-флеша, — единственный источник информации это Read ID (0x9F), который возвращает MF ID (производитель), KGD (0x5D = «known good die») и EID. Ваш драйвер уже читает первые три байта (`qspi_psram_verify_id`, `memc_mspi_qspi_psram.c:324`). Ключевое: **плотность (размер) закодирована в битах EID** — и у AP Memory/Espressif (MF 0x0D), и у ISSI это несколько старших бит первого байта EID. Точную кодировку надо брать из даташита каждого вендора — она не стандартизована, esp-idf, например, делает ровно это для своих модулей. Таймингов и dummy-циклов в ID нет — их всё равно придётся держать в таблице по MF ID.

Отсюда принципиальное ограничение: автодетект работает только среди **известного драйверу белого списка** вендоров. Незнакомый MF → либо отказ с внятным логом, либо фолбэк на generic-параметры из DT.

## Что нужно сделать в драйвере

1. **Триггер режима.** Узел с `compatible = "qspi-psram"` без указания части и без полного набора generic-свойств → драйвер идёт в детект. Либо явное булево свойство `auto-detect` — так честнее, чем угадывать по отсутствию свойств.

2. **Последовательность.** Уже готова: `qspi_psram_force_spi_mode` → `qspi_psram_reset` → Read ID на низкой частоте (24 МГц init-конфиг). Дописать: читать не 3, а ~8 байт (полный EID), распарсить MF + биты плотности → размер.

3. **Таблица ID → параметры.** Небольшая, ключ — MF ID: набор команд (QPI/SPI), rx/tx dummy, tCEM и границу страницы для `ce-break-config`. Размер берётся не из таблицы, а из EID. Это ровно та C-таблица, которую swift-tk просит убрать из текущего PR — но здесь у неё появляется оправдание: эти данные **невозможно** положить в DT, потому что DT описывает известную плату, а автодетект нужен как раз тогда, когда часть заранее неизвестна.

4. **Валидация.** KGD ≠ 0x5D → чипа нет или он бракованный, отказ. Дополнительно (или как фолбэк для незнакомого MF) можно определять размер классическим wrap-тестом: записать маркеры по адресу 0 и по степеням двойки, найти, где начинается алиасинг — у драйвера уже есть `qspi_psram_command_read/write` с адресной фазой, этого достаточно.

## Главная проблема: донести размер до контроллера

Определённый размер легко отдать приложению через `memc get_size` (`data->mem_size` — вы это и называли мотивацией в треде). Но с memory-mapped режимом хуже. Я проверил STM32-контроллер: `DeviceSize` (DEVSIZE в DCR1) зашивается **на этапе компиляции** из DT-свойства `size` дочернего узла — `.DeviceSize = MSPI_STM32_INST_MEM_ADDR_BITS(index, 26)` в `mspi_stm32_ospi.c:1524`, программируется при init контроллера, до того как PSRAM-драйвер вообще запустился. `mspi_stm32_ospi_memmap_on()` DEVSIZE не перепрограммирует, и в `mspi_dev_cfg` поля размера нет.

То есть варианты:

- **Вариант A (честный минимум):** на memory-mapped контроллерах `size` в DT остаётся обязательным, а автодетект играет роль верификации — прочитали ID, сравнили с DT, при расхождении ругаемся или отказываем. Плюс автоматика для не-mapped доступа. Ничего вне драйвера менять не надо.
- **Вариант B (полноценный):** расширить STM32 mspi-драйвер, чтобы он брал размер окна из `memmap_cfg.size` в момент `mspi_memmap_config()` (поле в структуре уже существует, контроллер его просто игнорирует) и перепрограммировал DEVSIZE. Тогда PSRAM-драйвер подставляет найденный размер в рантайме. Это отдельный PR в чужую зону (swift-tk/erwango), с согласованием семантики на уровне MSPI API — не только для STM32.

Реалистичный путь — A сначала, B как развитие.

## Что такое маска и зачем она

Маска — это способ сказать при сравнении: «эти биты важны, а эти — игнорируй». Проблема, которую она решает: ответ чипа на Read ID состоит из двух частей — **постоянной для модели** (производитель, KGD, биты плотности) и **уникальной для экземпляра** (номер лота, координаты кристалла на пластине). Сравнивать надо только первую часть, а где проходит граница — у каждого вендора своё. Маска позволяет описать эту границу данными в таблице, а не логикой в коде.

## Механика

В записи таблицы лежат два массива одинаковой длины: эталон `id[5]` и маска `mask[5]`. Сравнение — побитовое И с маской обеих сторон:

```c
static bool id_match(const uint8_t *read, const struct qspi_psram_id_entry *e)
{
    for (int i = 0; i < 5; i++) {
        if ((read[i] & e->mask[i]) != (e->id[i] & e->mask[i])) {
            return false;
        }
    }
    return true;
}
```

Бит маски = 1 → бит участвует в сравнении. Бит маски = 0 → бит вычёркивается с обеих сторон (`x & 0 == 0` всегда), то есть его значение не влияет на результат. Маска работает с точностью до бита, не до байта — это важно, потому что граница «постоянное/уникальное» проходит посреди байта.

## Разбор на реальном примере

У APS6404 (кристалл ESP-PSRAM64H) ответ на 0x9F устроен так:

```
байт 0: MF ID   = 0x0D          — производитель, постоянный
байт 1: KGD     = 0x5D          — годный кристалл, постоянный
байт 2: EID[47:40]              — старшие 3 бита = плотность, младшие 5 бит = начало трейс-данных
байт 3: EID[39:32]              — трейс-данные (лот/позиция), у каждого экземпляра свои
байт 4: EID[31:24]              — трейс-данные
```

Запись таблицы для этой части:

```c
{
    .name = "ESP-PSRAM64H",
    .id   = { 0x0D, 0x5D, 0x40, 0x00, 0x00 },  /* 0x40 = плотность 010 в битах [7:5] */
    .mask = { 0xFF, 0xFF, 0xE0, 0x00, 0x00 },
    ...
}
```

`0xE0` = `1110 0000`: сравниваем только три старших бита байта 2 (плотность), пять младших игнорируем. Байты 3–4 замаскированы целиком.

Теперь два физических экземпляра одной модели:

```
чип А: 0D 5D 46 8A 31        чип Б: 0D 5D 5B C2 07
       │  │  │└┴─┴── трейс          │  │  │└┴─┴── другой трейс
       │  │  └ 010 + мусор          │  │  └ 010 + другой мусор
```

Побайтово после наложения маски:

| байт | маска | чип А `& mask` | чип Б `& mask` | эталон `& mask` |
|---|---|---|---|---|
| 0 | 0xFF | 0x0D | 0x0D | 0x0D |
| 1 | 0xFF | 0x5D | 0x5D | 0x5D |
| 2 | 0xE0 | 0x46→**0x40** | 0x5B→**0x40** | 0x40 |
| 3 | 0x00 | 0x8A→**0x00** | 0xC2→**0x00** | 0x00 |
| 4 | 0x00 | 0x31→**0x00** | 0x07→**0x00** | 0x00 |

Оба совпали с эталоном, хотя их сырые ID различаются в трёх байтах из пяти. Голое `memcmp` на 5 байт признало бы оба чипа «неизвестными» (или совпал бы ровно один — тот, с которого списывали эталон).

А ESP-PSRAM32H отличается от 64H только битами плотности в байте 2 (например `001` вместо `010`) — это отдельная запись с тем же `mask`, но другим `id[2]`, и она корректно отличится, потому что биты плотности как раз *внутри* маскируемой зоны сравнения.

## Что маска даёт бесплатно

**Короткие ID.** Ваше опасение «чип отдаёт меньше 5 байт» перестаёт быть проблемой: для части с коротким ID хвостовые байты маски просто нули, и что бы шина ни вернула за пределами реального ID — повтор по кругу, мусор, 0xFF с подтяжек — на сравнение это не влияет. Гарантия wrap-around не нужна.

**Отсев брака и пустой шины.** KGD в сравнении участвует (маска 0xFF), поэтому бракованный кристалл (у AP Memory он отвечает 0x55 вместо 0x5D) не совпадёт ни с одной записью. Туда же — отсутствующий чип: шина отдаст 0x00 или 0xFF во всех байтах, что не совпадёт по MF. Для внятной диагностики стоит после неудачного прохода по таблице сделать две отдельные проверки: все байты 0x00/0xFF → «чип не отвечает», MF известен, но KGD = fail-значение → «die failed», иначе → «неизвестный чип, ID: …».

**Полное совпадение как частный случай.** Ваша исходная идея не отменяется, а вкладывается: запись с маской из сплошных 0xFF — это и есть точное сравнение всех 5 байт, если вдруг попадётся вендор, у которого весь ID постоянный.

## Два практических правила

1. **Порядок записей — от специфичных к общим.** Если когда-нибудь появится запись-фолбэк вида «любой AP Memory» (маска только на MF+KGD), она должна стоять после конкретных частей, а поиск — останавливаться на первом совпадении. Иначе общая запись перехватит всё.
2. **Маску для каждой записи сверять с даташитом, а не копировать.** Раскладка EID у ISSI не обязана совпадать с AP Memory — сколько бит занимает плотность и где начинаются трейс-данные, надо один раз посмотреть в разделе Read ID конкретного даташита. Маска как раз и хороша тем, что вся вендорская специфика сидит в двух массивах данных, а код сравнения один и никогда не меняется.

**1. Кодировка плотности сталкивается между семействами.** Код `n` в EID[47:45] означает `16 Мбит << n` у AP-линии, но `8 Мбит << n` у ISSI. То есть `010` — это 64 Мбит у AP и 32 Мбит у ISSI.
```
0D 5D 000 → AP-family 16Mb    9D 5D 000 → ISSI 8Mb
0D 5D 001 → AP-family 32Mb    9D 5D 001 → ISSI 16Mb
0D 5D 010 → AP-family 64Mb    9D 5D 010 → ISSI 32Mb
0D 5D 011 → AP-family 128Mb   9D 5D 011 → ISSI 64Mb
```

## Почему tCEM не подбирается тестом

Надо понимать, что физически происходит при нарушении tCEM. PSRAM — это DRAM со встроенным самообновлением, и пока CE# удерживается низким, внутренний рефреш **заблокирован**. Превышение tCEM портит не те данные, которые вы сейчас передаёте — оно срывает рефреш **других строк**, которым он был нужен именно в этот момент. Отсюда три свойства отказа, убивающие идею подбора:

1. **Отказ вероятностный, а не детерминированный.** Пострадает ли что-то — зависит от того, какие строки ждали рефреша во время нарушения и насколько слабые в них ячейки. Короткий тест может тысячу раз пройти на нарушенном тайминге и упасть на тысяча первый.

2. **Порог зависит от температуры экспоненциально.** Время удержания заряда в ячейке падает с нагревом — именно поэтому грейды и различаются (8 мкс при 85°C против 3 мкс при 105°C у AP). Тест при init на столе при 25°C радостно «подтвердит» и 20 мкс, а летом в закрытом корпусе устройство начнёт тихо портить данные. Вы бы калибровали параметр по той единственной переменной, которую при загрузке контролировать не можете.

3. **Порог зависит от худшей ячейки кристалла.** Retention у ячеек разбросан; производитель гарантирует tCEM по худшей ячейке при худшей температуре с запасом. Чтобы честно это проверить, нужно прописать весь массив, длительно удерживать данные через много циклов рефреша, вычитать, повторить с разными паттернами и температурами — это минуты стресс-теста при каждой загрузке, и всё равно без гарантии.

Тест может **доказать нарушение**, но не может **доказать безопасность** — классическая асимметрия. Показательно, что так не делает никто: ни esp-idf, ни один SDRAM-контроллер в мире не «подбирает» рефреш-тайминги экспериментально — они всегда берутся из спецификации или SPD.

## Чем консервативный дефолт реально грозит

Цена худшего случая измерима. В QPI на 80 МГц байт занимает 2 такта, накладные расходы на транзакцию (команда + адрес + dummy + пауза CE) — порядка 0.2 мкс. При tCEM = 8 мкс в одно окно CE влезает ~300 байт полезной нагрузки, оверхед ~3%; при консервативной 1 мкс — ~40 байт, оверхед ~20%. Неприятно, но это деградация пропускной способности, а не целостности данных — и она полностью снимается одной строчкой `ce-break-config` в DT для тех, кто знает свой грейд. Правильный трейдофф для AUTO очевиден.

## Где эмпирика в авторежиме уместна

Тестирование при init — хороший инструмент для параметров с **детерминированным и мгновенным** отказом:

- **Размер через wrap-тест** — записать маркеры по степеням двойки, найти, где начинается алиасинг адресов. Отказ детерминирован, тест занимает микросекунды, температура ни при чём. Это честный фолбэк для неизвестного MF ID и перекрёстная проверка битов плотности (кстати, закрыл бы вопрос с подозрительной опечаткой в даташите APS3204).
- **Smoke-тест после init** — записать/вычитать паттерн по нескольким адресам. Неправильные dummy-циклы или команда чтения проявляются немедленно и стабильно (данные сдвинуты/мусор). Дёшево и отсекает грубую misconfiguration до того, как приложение начнёт работать с памятью.
- **Dummy-циклы** в принципе даже подбираются перебором (отказ детерминированный), но необходимости нет — они известны по семейству.

А частота — вообще не кандидат: во-первых, отказ на превышенной частоте тоже маргинальный (зависит от температуры, напряжения, качества разводки платы), во-вторых, это знание уровня платы, и оно уже обязано лежать в `mspi-max-frequency`. Единственная легитимная «калибровка» здесь — аппаратная подстройка точки сэмплирования (delay block / DQS-тренинг), которую STM32-контроллер делает сам, и это подстройка интерфейса, а не выбор лимитов чипа.

**Итоговое правило для AUTO:** тестировать можно то, что ломается сразу и всегда (адресация, протокол); нельзя — то, что ломается редко и хуже всего при худших условиях (retention/рефреш, частотный запас). tCEM — во второй категории: консервативный дефолт из таблицы + DT-override, и точка.

## Общая идея

Runtime-чтения devicetree в Zephyr не существует — во время сборки `gen_defines.py` превращает весь DTS в гигантский заголовок `devicetree_generated.h` из тысяч `#define`, а все `DT_*`-макросы просто **склеивают имя идентификатора из кусочков и проверяют, определён ли он**. `DT_INST_ENUM_HAS_VALUE` — типичный представитель этой механики.

## Шаг 0: что генерирует сборка

Для нашего узла с `chip-variant = "AUTO"` генератор, зная из биндинга, что свойство — enum, эмитит (реальная строка из сборки для cedar):

```c
#define DT_N_S_soc_S_spi_420d1400_S_psram_0_P_chip_variant_ENUM_VAL_auto_EXISTS 1
```

Имя читается как путь: `DT_N` (node) + путь `/soc/spi@420d1400/psram@0` (где `/`→`_S_`, `@`→`_`) + `_P_chip_variant` (property) + `_ENUM_VAL_auto_EXISTS`. Значение `"AUTO"` прошло через `str2ident`: **нижний регистр**, спецсимволы → подчёркивания. Вот почему в C-коде мы пишем `auto` маленькими буквами, хотя в YAML и DTS стоит `"AUTO"`.

Ключевое: этот `#define` существует **только если** у узла реально стоит `chip-variant = "AUTO"`. У узла с `"ESP64H"` вместо него будет `..._ENUM_VAL_esp64h_EXISTS 1`, а у узла вообще без свойства — ничего.

## Шаг 1: раскрутка до имени узла

```c
DT_INST_ENUM_HAS_VALUE(n, chip_variant, auto)
  → DT_ENUM_HAS_VALUE(DT_DRV_INST(n), chip_variant, auto)      // devicetree.h:4725
  → DT_ENUM_HAS_VALUE(DT_INST(n, DT_DRV_COMPAT), ...)          // :4333
```

`DT_DRV_COMPAT` у нас `qspi_psram`, так что `DT_INST(0, qspi_psram)` склеивается в `DT_N_INST_0_qspi_psram` — ещё один сгенерированный `#define`, который является **алиасом** полного пути: генератор пронумеровал все enabled-узлы с этим compatible и для каждого номера создал маппинг на `DT_N_S_soc_S_spi_420d1400_S_psram_0`.

## Шаг 2: склейка идентификатора

```c
#define DT_ENUM_HAS_VALUE(node_id, prop, value) \
	IS_ENABLED(DT_CAT6(node_id, _P_, prop, _ENUM_VAL_, value, _EXISTS))
```

`DT_CAT6` — это шесть операторов `##` подряд. Из наших аргументов собирается один длинный идентификатор:

```
DT_N_S_soc_S_spi_420d1400_S_psram_0 ## _P_ ## chip_variant ## _ENUM_VAL_ ## auto ## _EXISTS
= DT_N_S_soc_S_spi_420d1400_S_psram_0_P_chip_variant_ENUM_VAL_auto_EXISTS
```

Попутный ответ на вопрос, который вы могли не задать: `auto` — ключевое слово C, но здесь это безопасно. Token pasting происходит в препроцессоре **до** того, как компилятор разбирает ключевые слова, и `auto` становится серединой длинного идентификатора, а не самостоятельным токеном.

## Шаг 3: IS_ENABLED — превращение «определён/не определён» в 1/0

Прямо написать `#if <макрос>` с неопределённым макросом в выражении инициализатора нельзя. `IS_ENABLED` решает это трюком со «вторым аргументом»:

- Если склеенный макрос **определён как `1`**, внутри `IS_ENABLED` происходит ещё одна склейка `_XXXX ## 1` → `_XXXX1`, который определён как нечто с запятой внутри — из-за этого вспомогательный вариадик-макрос выбирает свой второй аргумент, литерал `1`.
- Если макрос **не определён**, склейка даёт неопределённое имя без запятой — выбирается третий аргумент, литерал `0`.

Никакой ошибки «undefined identifier» — просто честный compile-time `1` или `0`.

| `chip-variant = "AUTO"` | `..._ENUM_VAL_auto_EXISTS 1` | `1` |

## Зачем это вообще нужно: физика PSRAM

PSRAM — это DRAM-ячейки с встроенным самообновлением (refresh), спрятанные за SPI-интерфейсом. Пока чип выбран (CE# в активном состоянии), внутренний рефреш **заблокирован** — контроллер памяти не может одновременно обслуживать внешнюю транзакцию и обновлять строки. Отсюда два аппаратных ограничения, которые накладывает каждый даташит:

1. **tCEM** — максимальное время удержания CE# низким за одну транзакцию (8 мкс у AP-семейства, 4 мкс у ISSI при ≤85°C, 3/1 мкс у горячих грейдов). Превысил — какие-то строки пропустят рефреш и потеряют заряд. Тихая порча данных, причём не тех, что передаёшь, а соседних.
2. **Граница страницы/burst** — линейный burst не должен пересекать границу 1 КБ (у ISSI чтение/запись вообще всегда заворачивается внутри страницы). Пересёк — адрес заворачивается, и данные ложатся не туда.

Классический SPI-flash ничего такого не требует: ему всё равно, сколько держат CE#. Поэтому в общий API MSPI это добавили как отдельную, «PSRAM-ную» настройку.

## Что описывает свойство

`ce-break-config = <mem_boundary time_to_break>` — две ячейки, которые `MSPI_DEVICE_CONFIG_DT_INST()` кладёт в `mspi_dev_cfg.mem_boundary` (байты) и `mspi_dev_cfg.time_to_break` (микросекунды). Смысл — инструкция контроллеру: **«разбивай любую передачу так, чтобы ни один отрезок с удержанным CE# не пересёк эту границу адресов и не длился дольше этого времени»**. Ноль в ячейке = ограничения нет. Это устройство описывает свои требования, а исполнение — задача контроллера шины.

## Как это исполняет контроллер

Здесь важно понимать, что API лишь передаёт цифры, а реальный механизм у каждого контроллера свой:

- **Ambiq** (`mspi_ambiq_ap3.c:841-849`) — единственный в дереве, кто исполняет оба параметра аппаратно: `mem_boundary` превращается в `eDMABoundary` (DMA-движок сам рвёт транзакцию на границе), `time_to_break` — в `ui16DMATimeLimit` (таймер в единицах 0.1 мкс, `time_to_break * 10`), по истечении которого контроллер снимает CE#, даёт чипу паузу tCPH на рефреш и продолжает. Причём на старом SoC без такой поддержки драйвер честно возвращает ошибку, если значения ненулевые.
- **STM32 OSPI/XSPI** (`mspi_stm32_ospi.c:640-644`) — значения **только сохраняются** в `data->dev_cfg`, но на железо не влияют. Реальная защита у STM32 — регистр `CSBOUND` в DCR3: CE# автоматически снимается при пересечении границы 2^N байт, и берётся она из свойства *контроллера* `st,csbound`. Именно поэтому в оверлеях платы стоит `st,csbound = <7>` — 128 байт на одно удержание CE#, что при 50 МГц QPI ≈ 5 мкс и укладывается даже в 4-мкс… нет, стоп: 128 байт × 2 такта / 50 МГц = 5.1 мкс — это **не** укладывается в 4 мкс ISSI, и тем более в worst-case 1 мкс. Это отдельная тема ниже.
- **DesignWare, эмулятор** — хранят, не используют.

То есть на STM32 `ce-break-config` сегодня — декларация без исполнителя. Механизм работает по-настоящему только там, где контроллер его поддерживает.

## Как этим пользуется наш драйвер

В таблице у каждой записи два поля: `ce_max_burst_bytes` (страница, 1024 у всех) и `ce_refresh_us` (tCEM из даташита). При построении `dev_cfg` они ложатся в `mem_boundary`/`time_to_break` и уходят в контроллер через `mspi_dev_config()`. Логика по режимам:

- **именованный** — значения из таблицы (даташит стандартного грейда);
- **AUTO** — `time_to_break` заменяется worst-case семейства (`QSPI_PSRAM_WORST_TCEM_US`: 3 мкс AP, 1 мкс ISSI), потому что грейд из ID не читается; затем каждая ненулевая ячейка `ce-break-config` из DT переопределяет своё поле — пользователь, знающий грейд, может ослабить;
- **generic** — что задано в DT, то и уходит, без проверок (лишь предупреждение про `rx-dummy`).

## О чём стоит помнить на вашей плате

Раз STM32 исполняет только `st,csbound`, безопасность tCEM там определяется исключительно этим свойством и частотой: `2^(csbound+1)` байт на удержание CE#. Для IS66WVS4M8BLL при 50 МГц QPI:

| `st,csbound` | байт на CE# | время удержания |
|---|---|---|
| 7 | 128 | ~5.1 мкс + оверхед — **больше 4 мкс** |
| 6 | 64 | ~2.6 мкс — укладывается в 4 мкс, но не в 1 мкс |
| 4 | 16 | ~0.6 мкс — укладывается даже в 1 мкс |

Стресс-тест на 100 циклов при `csbound=7` прошёл чисто — при комнатной температуре запас по retention большой, и это ровно тот случай, о котором мы говорили: тест не может доказать безопасность нарушения tCEM, только его отсутствие сейчас. Формально для ISSI-чипа на этой плате корректнее `st,csbound = <6>`. Это уже настройка чужого драйвера контроллера, а не вашего, — но раз параметры из вашей таблицы на STM32 не исполняются, документировать это в биндинге стоит (там сейчас есть общая фраза «whether memory mapping is available… is up to the controller», а про CE-break — нет).

### 1. `mspi-io-mode` (строка 89): сузить `enum` до поддерживаемых значений и дать `default`

**`default: "MSPI_IO_MODE_SINGLE"` — прав, делать.** Унаследованное свойство из `mspi-device.yaml` дефолта не имеет, добавить новый ключ edtlib разрешает (`_merge_props` запрещает только *переопределять* уже заданные ключи). Заодно уйдёт корявая фраза «note that an omitted value means SINGLE».

**Сужение `enum` — ловушка, и тут erwango не прав в деталях.** Две проблемы:
- edtlib **запрещает** менять `enum` унаследованного свойства (`_bad_overwrite`, `edtlib.py:3119-3136`: всё, кроме description/required/title/compatible/examples, — ошибка «from included file overwritten»). Обходной путь — `property-blocklist` при include и полное переопределение свойства.
- Но главное: `MSPI_DEVICE_CONFIG_DT_INST` превращает строку в C-значение через **`DT_ENUM_IDX`** (`mspi/devicetree.h:42`) — то есть берёт **порядковый номер в списке enum биндинга**. Список `[SINGLE, QUAD]` даст QUAD индекс 1 = `MSPI_IO_MODE_DUAL` в C. Тихо неправильный режим шины. Показательно, что сам erwango в сниппете привёл не «SINGLE и QUAD», а префикс исходного списка из 7 значений — индексы сохраняются, но такой список по-прежнему пропускает DUAL-режимы, которые драйвер не поддерживает. Честного build-time ограничения ровно до {SINGLE, QUAD} этим механизмом не получить, пока общий макрос MSPI не перейдёт на `DT_STRING_TOKEN` (а это уже код swift-tk).

Ответ в тред: default принимаем; про enum объяснить индексную зависимость `DT_ENUM_IDX_OR` и оставить runtime-проверку в `check_dt_cfg` — она как раз и существует по этой причине.

### 2. Generic-режим (строка 28): два compatible — `qspi-psram` и `qspi-psram-generic`

Он реагирует на фразу «are checked at init and the driver refuses to probe without them»: зачем ловить отсутствие `read-command`/`size`/… в runtime, если отдельный биндинг с `required: true` поймает это на этапе сборки DT.
