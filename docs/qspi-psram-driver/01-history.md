### 11.08 — приведение PR в порядок, первый запуск на плате, tCEM

- **Переименование, начатое в веб-коммитах, ломало сборку молча**:

  compatible генерируется только `DT_HAS_QSPI_PSRAM_ENABLED` → драйвер

- Биндинг перенесён `dts/bindings/mspi/mspi-qspi-psram.yaml` →

  `is66wv`). Копирайт → `Copyright (c) 2026 Kirill Shypachov`.
- Squash трёх коммитов в один и rebase на `main`. **Rebase вскрыл
  переименование XIP → MEMMAP в MSPI API**: `mspi_xip_config` →
  `mspi_memmap_config`, `MSPI_XIP_*` → `MSPI_MEMMAP_*`, `CONFIG_MSPI_XIP` →
  `CONFIG_MSPI_MEMMAP`, DT `xip-config` → `memmap-config`.
- Проверка «два режима независимы»: код корректен, но описание биндинга
  ложно требовало `read-command` и т. п. при `chip-variant` — исправлено.
  В generic-режим добавлена проверка `cmd_length`/`addr_length`
  (иначе молчаливая «успешная» инициализация нерабочего устройства),
  `rx-dummy = 0` → предупреждение.
- Первая сборка (`samples/hello_world`, `b_u585i_iot02a`) — обе конфигурации
  линкуются. Находка: `st,psram-device` требует `read-command`/`write-command`
  (research §4.6).
- **Первый запуск на cedar_switch** (плата пользователя): Read ID возвращал
  нули — в минимальном тесте без драйвера NOR-флеш никто не мультиплексировал
  пины OCTOSPI1, которые PSRAM использует в muxed-режиме. Затем запись была
  полностью битой из-за `st,timing-config = <1>` в DTS платы: ST-драйвер
  вычитает turnaround из `tx_dummy` (= 0) → `uint16_t` 65535 dummy-циклов.
- Muxed FLASH + PSRAM: PASS (грубое и пословное чередование, одновременный
  memory-mapped обеих микросхем — флеш `0x90000000`, PSRAM `0x70000000`).
- XIP: первая ступень во внутренней флеш пишет образ в NOR, ICACHE remap
  `0x02000000 → 0x90000000`, прыжок. Потребовалось обнулить `MSPLIM/PSPLIM`
  и выключить MPU перед прыжком.
- **Порча PSRAM со смещения +0x800.** Claude последовательно выдвинул и сам
  опроверг гипотезы: запись/стирание флеш, ICACHE remap, muxed-режим.
  Настоящая причина — нарушение **tCEM**: плотный цикл записи держит nCS
  дольше 8 мкс, ST-контроллер CE внутри серии не отпускает. Любая пауза
  (1 мкс каждые 256 байт) → 0 ошибок. Утренние «30 чистых проходов» прошли
  потому, что тест был медленным (хеш на каждое слово).
- Анализ `mspi_stm32_ospi.c` (только чтение): `mem_boundary`/`time_to_break`
  сохраняются и никуда не программируются; CSBOUND берётся из `st,csbound`
  контроллера; REFRESH/MAXTRAN не заданы. Эксперимент `st,csbound` = 0/7/8/10
  подтвердил механизм (research §4.2).
- Решено: CE-break — ответственность контроллера, в PR драйвера это не
  чинится; `st,csbound` задаётся в DTS платы.
- Аудит «все свойства биндинга доходят до кода»: `size` был `required`, но не
  использовался; неверное описание `st,timing-config`; комментарий со
  ссылкой на несуществующий legacy-драйвер; нет проверки `mspi-data-rate`;
  не-ASCII символы.
- **`st,timing-config` удалён** из биндинга и драйвера вместе со всеми
  вендорными `#include` и `SOC_FAMILY_*` ветками — драйвер стал
  платформонезависимым.
- **`size` стал необязательным**: в таблицу добавлен `size_bits`, в named-режиме
  ёмкость берётся оттуда. Попутно выяснилось, что в DTS платы PSRAM занижен
  вдвое (32 Мбит при реальных 64).
- Исследование MEMC API и перекрытия с деревом: `memc_mspi_is66wv.c` (Nordic,
  11.06.2026) и `memc_mspi_aps6404l.c` имеют тот же набор команд.
  **Эксперимент: штатный `aps6404l` заводит ESP-PSRAM64H на этой плате**
  (после явного указания всех параметров передачи в DT); после тёплого сброса
  он читает мусорный vendor ID, предупреждает и продолжает.
