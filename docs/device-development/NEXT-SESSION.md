## Что P0 оставил для P2

Это прямо ложится на P2, а не ждёт своего этапа:

- **Модули P1 при интеграции лягут в SRAM, и правило relocation их молча
  пропустит.** `job_manager` один — 44 КБ .bss. Библиотеки лежат в `lib/`, а
  `gen_relocate_app.py` сопоставляет по имени каталога — нужен фрагмент
  `src/helpers/psram_sections.ld`, как у `settings_registry`. Проверять по map.
- **HTTP-сервер легко занять.** 4 клиентских слота и 10 с неактивности:
  частые запросы с коротким таймаутом держали сервер без ответа 180 с. Это
  ровно «корректная уборка при abort» и «2 клиента» из критерия P2.
- **Файловый бэкенд настроек медленный**: один `/lfs/settings` на реестр и
  Matter, чтение ключа по коду квадратично от длины файла, пять ключей — 0,58 с.
  Реестр читает ключи один раз при старте, так что `web-auth` на нём не
  платит за каждый запрос — но пишет в тот же файл. Решение о бэкенде
  (`MAX_LINES`, ZMS/NVS) — за владельцем, до P4.
- **HTTP только IPv4** (`0.0.0.0:80`, нет `[::]:80`) — вопрос к владельцу, P2.
- **Setup-token по решению владельца отображается в веб-интерфейсе**, там же
  кнопка окна commissioning. Открытая оговорка в разделе 13: token в самом
  интерфейсе не доказывает физический доступ. Уточнить до проектирования
  `web-auth`, не придумывать.
- **Язык интерфейса — русский**, словарь строк с первого экрана.
- **Веб только показывает Matter fabrics**, без удаления.

## Задача P2

Критерий из раздела 10: «UI работает офлайн, 2 клиента, нет обхода авторизации
через legacy, корректная уборка при abort». Работа делится на две половины,
которые встречаются в контракте: `web-api`/`web-auth`/`web-assets` на устройстве
и приложение в браузере.

### Чем P1 помогает

Mock существует именно для того, чтобы фронтенд писался и гонялся e2e до того,
как на устройстве появится первый HTTP-обработчик. Запуск:

    cd tools/api-contract
    python -m cedar_contract.mock --port 8080
    python -m cedar_contract.mock --scenario setup_required=false

Устройство, которое он изображает, стартует **ненастроенным**: `/auth/state`
отвечает `setup_required: true`, а `POST /auth/setup` требует заголовок
`X-Setup-Token: cedar-mock-setup-token`. При `setup_required=false` пароль
администратора — `cedar-mock-admin`. Ни то ни другое не секрет, оба печатаются
при старте.

Для сценариев, до которых иначе не дойти, есть `/__mock/*` — вне `/api/v1`,
которого устройство не отдаёт: `advance` проматывает время (таймаут
подтверждения сети — 120 секунд, ждать его в тесте никто не будет), `scenario`
включает неудобный случай (scan на 64 записи, образ, не прошедший проверку,
offline C6, install не по Ethernet), `reset` возвращает свежее устройство.
Фронтенд, который начнёт от `/__mock` зависеть, сразу же сломается о настоящее
устройство — это правильный способ такой ошибке обнаружиться.

Ещё одно: `MockApp` — это функция из значения `Request` в значение `Response`,
без сокетов. Тот же приём стоит применить к `web-api`: ядро решает, адаптер
делает I/O. И middleware mock'а — рабочий образец порядка проверок, который
контракт требует от устройства: аутентификация до CSRF, CSRF до тела, лимит до
разбора, ключ идемпотентности до обработчика.

### Что сделать в P2 (из раздела 4 и раздела 10)

1. **Выбор стека фронтенда.** Три ограничения из раздела 4: итоговый `dist` ≤ 512
   КиБ gzip, сборка воспроизводится по lockfile через `npm ci` без сети сверх
   registry, приложение работает без CDN и внешних шрифтов. Это вопрос к
   владельцу, а не свободный выбор.
2. **Генерация типов из openapi.json.** Ручное дублирование схем в коде
   запрещено, расхождение должно ловиться сборкой. Тут же стоит закрыть пятую
   контрактную проверку: когда появится таблица маршрутов `web-api`, её можно
   сравнить с тем же индексом документа, по которому роутит mock
   (`Document.operations`, `MockApp.uncovered`).
3. **`web-auth`.** Параметры KDF, жизненный цикл сессии, expiry, CSRF и Origin,
   rate limit, атомарность первичного setup. Раздел 12 требует sim-набор на всё
   это; задержка KDF на реальном CPU под нагрузкой — аппаратная строка.
4. **`web-api`.** Маршрутизация, парсинг, лимиты, коды ошибок через
   `api-validation`, фрагментированный body, abort, неизвестные поля, повтор с
   тем же ключом. Здесь же — разделить SPA fallback и JSON 404 (сейчас
   обработчик неизвестных URL перенаправляет на `/`) и закрыть обход новой
   авторизации через legacy `/upload` на 8080.
5. **`web-assets`.** MIME, ETag, gzip, политика кеша index, SPA fallback против
   JSON 404.
6. **Экран обзора и экран доступа** — login, setup, смена пароля, logout, плюс
   явное предупреждение, что соединение идёт по HTTP в доверенной локальной сети.
7. **Локализация с первого экрана.** Строки в один словарь; язык — русский.

## Как работать

Набор тестов, который проходит с первого раза, ничего не доказывает. Проверяй
его мутациями реализации: ломай по одному решению и смотри, что набор это
ловит.

Не полагайся на описания в документации без проверки. Если вывод важен,
измеряй. В P0 так выяснилось, что «180 секунд без HTTP на старте» создавал
сам скрипт замера, а «зависания шелла» в smoke были потерянными байтами UART.

Перед тем как чинить, убедись что дефект настоящий: один «баг» оказался
устаревшим бинарником, одна «поломка» — голоданием потока, а не зависанием.

**Коммиты не делай сам.** Доведи работу, прогони тесты, оставь всё в рабочем
дереве и скажи, что во что складывается. Коммитит владелец.

## Работа с платой

Для P2 плата понадобится ближе к концу — 2–4 клиента одновременно и p95
статусных запросов это аппаратные строки. Сбросы — только согласованные.

ST-LINK V3SET, серийник 002F002B3233510739363634. **Номер порта консоли
меняется между сессиями** (был 11303, в P0 — 21103): ищи по серийнику,
`tests/bench/bench_console.py` делает это сам. USB CDC платы с VID `0x2fe3` —
мост к UART C6. Проводной интерфейс хоста к плате — en7 (192.168.88.17),
Wi-Fi en0 не используй для IPv6. Плата — 192.168.88.14,
fe80::8234:28ff:fe10:1273.

Прошивка только приложения, MCUboot уже во внутренней флеш и его трогать не
надо:

    CLI="/Applications/STMicroelectronics/STM32Cube/STM32CubeProgrammer/STM32CubeProgrammer.app/Contents/Resources/bin/STM32_Programmer_CLI"
    EL=$PWD/CLIVEONE-W25Q128_STM32U545-PB10-PA4-PB1-PB0-PA7-PA6.stldr
    "$CLI" -c port=swd sn=002F002B3233510739363634 mode=NORMAL -el "$EL" \
       -w <build>/cedar_switch_3in4out_power/zephyr/zephyr.signed.bin 0x90000000 -v
    "$CLI" -c port=swd sn=002F002B3233510739363634 mode=NORMAL -hardRst

Именно mode=NORMAL: UR и HOTPLUG отваливаются с "Unable to get core ID".
Замеры старта и smoke — `tests/bench/boot_cycle.py` и `smoke.py`.

Если порт занят — это CLion держит его своим serial monitor: `lsof /dev/cu.usbmodem*`.

**Реле:** OUTPUT1..4 = выводы 21/24/25/28 = PA5/PC4/PC5/PB2 — по схеме,
расхождения нет. В DTS они `ACTIVE_LOW`, а катушки через ULN2003: при
логическом «выключено» катушки под током и светодиоды горят (подтвердил
владелец), каждый сброс отпускает и снова притягивает все четыре. Решение о
полярности — за владельцем.

## Что известно и не надо перепроверять

Поток W5500 создаётся как K_PRIO_COOP(2) и внутри while(int_pin) делает
синхронный опросный SPI, не уступая процессор. Любой достаточный поток в
сегменте снова задушит логи и шелл. **Владелец принял это как известный риск
до P8.** В апстриме — открытый PR #115626 (не issue), без ревью; он же
добавляет проверку длины кадра, отсутствие которой дало BUS FAULT в
`w5500_rx` после сброса C6 (`reports/p0/fault-c6-reset/`).

Транспорт ESP-Hosted после сброса C6 не восстанавливается без сброса STM32.

Биты Sn_MR охарактеризованы на железе двумя методами: MMB режет только
IPv4-мультикаст, MIP6B — только IPv6-мультикаст. MIP6B на этом изделии
применять нельзя: ломает Neighbor Discovery и SLAAC, а Matter живёт на
IPv6-мультикасте.

Патч W5500 и две другие правки в чужом дереве zephyr сохранены в patches/,
процедура восстановления — в patches/README.md. **`west patch clean` в этом
workspace запускать нельзя**: его `git clean -d -f -x` снесёт чужую
неотслеживаемую работу в общем дереве zephyr, включая нужный нам submanifest
esp-serial-flasher.

Вне west workspace Zephyr игнорирует `ZEPHYR_EXTRA_MODULES` целиком
(`zephyr_module.cmake` уходит в ветку `else()`), и сборка падает с «undefined
symbol JOB_MANAGER». `west init -l` создаёт workspace, ничего не выкачивая.

Флаги сброса RCC к моменту шелла уже очищены Matter — причину старта с платы
не прочитать.
