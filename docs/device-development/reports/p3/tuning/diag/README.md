# Диагностика: почему File + SPI interrupt медленнее на сборке 09-14

Исходный факт (полные попытки, каждая со стиранием раздела, tuning/file): один
`CONFIG_SPI_STM32_INTERRUPT=y` на образе 2026-09-13 19:12 — 43,59 / 43,49 / 43,62 с (027,
036, 037 на 10 циклах); тот же `.config` на образе 09-14 11:03 — 59,65 с (039); сочетания
на образах 09-14 — 58,88–60,61 (032, 033, 035). База без interrupt: 09-13 — 53,30 (опора
6 баз), 09-14 — 52,84 (038). У ZMS interrupt на образах 09-14 быстр (comboA 2,41–2,72),
база 09-14 как старая (040: 4,52). Различие образов по `nm`: код после eth_w5500 сдвинут
на 0x78 (eth_w5500.c изменён другим потоком 09-13 23:52), у 039 ещё esp_hosted_mcu.

Все прогоны ниже — без сборок и без правок исходников; образы из scratchpad.

## Загрузка потоков в покое (`threads_idle.py`, 11:49–12:15)

`kernel thread list` дважды через 60 с, доля времени потоков за окно:

| Образ | idle | shell_uart | CHIP | eth_w5500 | rx_q[0] |
|---|---|---|---|---|---|
| int-0913 (interrupt, 09-13) | 91,98 % | 4,13 | 1,59 | 1,29 | 1,00 |
| int-0914 (interrupt, 09-14) | 93,85 % | 4,34 | 0,63 | 0,81 | 0,35 |
| base-0913 (polled, 09-13) | 93,20 % | 3,51 | 1,46 | 0,92 | 0,88 |
| base-0914 (polled, 09-14) | — | — | — | — | — |

Лишнего потока нет; сеть в медленном образе занимает меньше. base-0914: консоль
потеряла байты («storagebench», «kernel thread lit») — данных нет (сбой обвязки, исправлен
проверкой эха в следующих скриптах). Время в обработчиках прерываний эта статистика не
видит.

## Счётчики ICACHE (`icache_monitor.py`, 12:15–12:27) — метод снят

CR = 0x1 — ICACHE включён в режиме 1-way (direct mapping, ставит MCUboot; приложение
сменить не может — выключение ICACHE снимает ремап 0x0200_0000 → 0x9000_0000). За 13 с
покоя 1,83 млн попаданий, MMONR (16 бит) насыщен — промахов ≥3,45 %, сравнить образы
окнами шелла нельзя. Потерянный байт превратил запись в CR в запись по 0x4003040 →
BUS FAULT (12:17). Гипотеза «коллизии прямого кеша при другой раскладке» не проверена.

## Сеть выключена (`net_off.py`, 12:27–12:35, вопрос владельца)

`net iface down 1` (eth0, W5500: `w5500_hw_stop` — SIMR = 0, сокет закрыт) и затем
`net iface down 2` (wlan0, esp_hosted), потом оба подняты; storage_bench 3, средние, мс:

| Образ, файл | Стадия | open+close | read 32 | read 1024 | load_one (hit) |
|---|---|---|---|---|---|
| int-0914, 4087 Б | все подняты | 17,5 | 30,5 | 25,8 | 626 |
| | eth0 down | 17,5 | 30,7 | 25,8 | 623 |
| | eth0 + wlan0 down | 17,5 | 30,5 | 25,8 | 623 |
| | снова подняты | 17,5 | 30,6 | 25,8 | 624 |
| int-0913, 4164 Б | все подняты | 15,4 | 22,9 | 18,4 | 749 |
| | eth0 down | 15,4 | 23,0 | 18,4 | 749 |
| | eth0 + wlan0 down | 15,4 | 22,9 | 18,4 | 749 |
| | снова подняты | 15,4 | 22,9 | 18,4 | 750 |

**Вывод: сеть (W5500 и Wi-Fi, вместе с их прерываниями) скорость чтения файловой системы
не меняет** — стадии совпадают в пределах 1 % на обоих образах. Отключать сеть физически
или собирать образ без W5500 не нужно (последнее к тому же сдвинуло бы раскладку кода).

## Оговорка: bench в покое между прогонами не сравним

Один и тот же образ int-0913: в 11:49 (файл 3702 Б) read 1024 — 11,8 мс, load_one —
400 мс; в 12:31 (4164 Б, те же 11 записей) — 18,4 и 749 мс. На неочищенном разделе время
чтения зависит от раскладки файла по блокам LittleFS (дописывания, сжатия, позиция
в блоках) сильнее, чем от образа. Поэтому сравнение «int-0914 читает вдвое медленнее
int-0913» из `threads_idle` доказательством не является. Доказательная база различия
сборок — только полные попытки со стиранием раздела (см. начало).

## Что остаётся открытым

Причина разницы 43,5 / 59,6 с между сборками 09-13 и 09-14 при одинаковом `.config`.
Сеть исключена; отличие — раскладка кода. Проверки, которые различат гипотезы, требуют
решения владельца: пересборка MCUboot с ICACHE 2-way, перенос горячего пути SPI/флеш
в SRAM (правка приложения), или пересборка на исходниках без изменения eth_w5500.c
(откат чужой незакоммиченной правки в общем дереве).
