use-fast-read удалён (обычное чтение 0x03 вместо 0x0B на тех же 80 МГц): хуже базы, commissioning 4/5 из-за хранилища — узел 104: перед окном Long dispatch 21 с, PASE и ArmFailSafe прошли, после CSR команда не дождалась ответа (CommandSender Timeout, 118 с). Повтор не нужен.

Цифры: старт на чистом разделе 2,8 с (база 1,9), старт с fabric 9,5 / 25,9 / 65,5 / 5,9 (без fabric) / 21,5 с — среднее/макс 25,7/65,5 (база 21,0/48,2), удаление 16,0 / 36,6 / 83,1 / 1,1 / 30,2 — 33,4/83,1 (29,6/60,8), commit 2,3–4,4 с. bench: open+close 19,8 мс (7,0), read 32 20,1 (12,8), read 1024 17,2 (8,9) — сырые чтения файла вдвое медленнее, а чтение ключа 308 мс (317) — нет. Медленнее и криптографические фазы: attestation 5,2 с (3,4), csr 4,0 (3,6).

Причина не установлена. По spi_nor.c без use-fast-read меняется только команда чтения (нет пустого байта), частота и деление на куски те же. Гипотеза «0x03 на 80 МГц вне спецификации W25Q → ошибки чтения → перечитывание LittleFS по CRC» логом не подтверждена: ошибок LittleFS/флеша сверх штатных нет (но несовпадения CRC данных LittleFS не логирует). Замедлены и фазы без хранилища — похоже на общее замедление системы. У ZMS та же настройка дала шум (025 zms). Для итога не важно: fast read оставить включённым, как в базе. Если причина нужна — замер SPI логическим анализатором или повтор попытки.
