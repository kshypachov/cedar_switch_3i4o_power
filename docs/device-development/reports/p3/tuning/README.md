Статус: **в работе** (начато 2026-09-13). Итоги появятся в конце этого файла.

## Методика (зафиксирована до перебора, не менялась)

Одна попытка = один образ = один прогон `run_trial.py` из 5 циклов:
прошивка → `storage_wipe yes` → старт на чистом разделе → перезагрузка и проверка
чтения (`mt/ctr/reboot-count` +1, тот же `mt/cfg/unique-id`) → 5 × (перезагрузка,
commissioning chip-tool, перезагрузка, `matter fabric reset`) →
`storage_bench 3 mt/cfg/unique-id` → перезагрузка и проверка сохранности
(счётчик перезагрузок Matter = число загрузок после стирания).

Алгоритм владельца: от базы меняется **одна** настройка, прогон, откат, следующая.
В конце — комбинация лучших значений, подтверждение тем же прогоном и прогоном из
10 циклов.

**Оценка попытки** (меньше — лучше), по циклам попытки:

    score = median(старт Matter с fabric) + median(удаление fabrics) + median(фаза commit)

- старт Matter: `Init CHIP stack` → `Matter stack initialized` (uptime платы);
- удаление: `matter fabric reset` → `Matter fabrics after delete` (время хоста);
- `commit`: `Received CommissioningComplete` → `was committed to storage`.

Дополнительно: `slope` = (старт с fabric в последнем цикле − в первом) / (циклов − 1), с/цикл.

**Порог значимости**: размах (max − min) оценок первых трёх прогонов базы подряд.
Опорное значение — медиана оценок всех прогонов базы бэкенда (база повторяется
примерно каждые 20 попыток). Попытка «лучше», если `score < опорное − порог`,
«хуже», если `score > опорное + порог`, иначе «в пределах шума». Попытка с
потерянным commissioning, проваленной проверкой чтения или сохранности не
сравнивается. Фазы `pase`, `attestation`, `csr` — контроль (криптография, от
бэкенда не зависят).

Попытки, упавшие из-за сборки, скрипта или консоли, в лимит не входят, но
записываются (каталог попытки с `aborted` в `metrics.json`).

**Почему кеш LittleFS не может держать весь файл настроек** (разбор по коду
`modules/fs/littlefs` 2.11 и `subsys/settings/src/settings_file.c`, вопрос владельца):

- Буферов три — кеш чтения `lfs->rcache`, кеш записи `lfs->pcache`, кеш каждого
  открытого файла — но размер у всех один `cache_size` (`lfs.c:4286`, `4297`, `3197`;
  в `lfs_config` отдельного размера нет, `read_buffer`/`prog_buffer` «Must be
  cache_size»). `read_size`/`prog_size` — гранулярность операций, не кеши.
- `cache_size` должен делить `block_size` (`lfs.c:4247`), блок здесь 4096 — а файл
  настроек 1,7–7,5 КБ (бенч: 1676 при MAX_LINES 48, 3548 в базе, 7555 при 256).
  Встраивание файла в метаданные ограничено `block_size/8` = 512 байт.
- Кеш файла выделяется в `fs_open` и освобождается в `fs_close` (`littlefs_fs.c:307`,
  `269`), а бэкенд settings открывает файл на каждое чтение ключа — кеш файла всегда пуст.
- Кеш чтения — одно окно (блок, смещение, размер) и сбрасывается при каждой
  синхронизации (`lfs_bd_sync`, `lfs.c:217`) и при проверке записи (`lfs.c:194`);
  settings закрывает файл после каждого `settings_save_one` → каждая запись Matter
  обнуляет кеш чтения. Отсюда 017 (4096): бенч без записей быстрее, путь Matter нет.
- Штатными настройками отдельного, переживающего записи кеша не получить; нужен
  либо код (держать файл открытым / копия настроек в RAM — правка Zephyr или
  приложения, решение владельца), либо бэкенд с чтением по ключу (ZMS).

## Изменение в прошивке для замера

`storage_bench [rounds] [key]` — необязательный ключ для замера «hit» (раньше

- Главный рычаг — кеш поиска ZMS: ячейка хранит адрес последней ATE; при общей
  ячейке поиск идёт назад по всей истории, по SPI-транзакции на ATE. 128/512 хуже
  базы, 1024 лучше, плато с 1536; без кеша commissioning срывается (PASE timeout).
- Прерывания SPI добавляют ~0,25 с сверх кеша и ускоряют даже фазы с криптографией:
  при опросе драйвер крутится в потоке-читателе. storage_bench при этом медленнее.
- Не помогли (шум): LL cache off, LOAD_SUBTREE_PATH off, collision bits 2, block
  size 64/256, SPI 40 МГц, fast read off, NOR sleep/erase, сектора 8/16/64 и ×2
  (за 5 циклов GC не наступает). Хуже: NO_DOUBLE_WRITE, кеш 128/512.
- Выше шума, но в итог не взяты: обычный хеш ячеек (FOR_SETTINGS=n) — вровень, но
  ключи делят ячейки (hit 45–82 мс); NO_LL_DELETE — мёртвые узлы копятся;
