# P5 — заметки по источникам логов (esp32-log-source, zephyr-log-source)

Записываются по ходу работы; сводка переносится в `README.md` отчёта.

## Фикстура ROM-потока C6 платы B

`tests/fixtures/esp32/board-b-rom-link-check.log` — копия
`reports/board-b/logs/05-coprocessor-link-check.log` основного дерева (sha256
`d12f51fa…`). Это консоль `tests/coprocessor_link_check`: сначала лог старта самого
STM32 (MCUboot, PSRAM), затем то, что USART3 принял от C6, между строками-маркерами
теста `--- normal boot (expect ROM banner + invalid header) ---` и
`--- normal boot (expect ROM banner + invalid header): 28528 bytes ---`. Сюита
подаёт только эту часть: 27 524 Б.

Что в ней (подсчитано скриптом по байтам, закреплено в тестах):

| Что | Число |
|---|---|
| строк по концам строк | 1016 |
| ровно `invalid header: 0xffffffff` | 983 (остальные — с потерянными байтами: `invaid`, `0xfffffff`) |
| `rst:0x1 (POWERON),boot:0xc (SPI_FAST_FLASH_BOOT)` | 1 |
| `rst:0x7 (TG0_WDT_HPSYS),boot:0xc (SPI_FAST_FLASH_BOOT)` | 3 — ROM без прошивки перезапускается сторожевым таймером |
| строк, **начинающихся** с `ESP-ROM:` | 0 |
| `ESP-ROM:` внутри строки | 3: `invalid header: 0xff<e6>ESP-ROM:esp32c6-20220919` |

Особенности захвата: тест печатал непечатаемые байты как `<hh>` (первый баннер
съеден — `<00>-20919`), консоль превратила CRLF в LF. Байтов вне ASCII-печатных и LF в
файле нет. Вторая сюита восстанавливает сырой поток (`<hh>` → байт, LF → CRLF).

**Вывод для дизайна:** сброс C6 обрывает строку, и баннер приходит посреди неё.
Правило «строка начинается с `ESP-ROM:`» не заметило бы ни одного из трёх
WDT-сбросов. Ассемблер начинает новую строку на `ESP-ROM:` в любом месте (и в
отбрасываемом хвосте длинной строки); оборванная часть уходит отдельной записью без
`truncated` — её обрезал сброс, а не предел 512 Б.

## esp32-log-source: решения

- Серия заменённых байтов (управляющие, битый UTF-8) — одна U+FFFD: пачка NUL от C6 в
  сбросе стоит 3 байта, а не заполняет строку.
- Таб сохраняется; DEL — U+FFFD.
- ESC + байт вне 0x20–0x7E: пропадает только ESC, байт — текст (или U+FFFD). CSI длиннее
  32 байтов параметров обрывается, дальнейшие байты — текст.
- Частичная строка по таймауту — без `truncated` (текст не резали, строку просто не
  закончили). Потеря байтов ring buffer (`note_overflow`) — U+FFFD и `truncated=true`.
- Время C6 из префикса ESP-IDF отбрасывается; текст записи — после `tag: `.
- Тег ESP-IDF: 1–64 байта до первого `:`, после которого пробел или конец строки;
  пробелы в теге допустимы (`esp image`).

## zephyr-log-source: решения

- Текст: `log_output_process()` без таймстемпа, уровня, цветов и имени источника
  (`SKIP_SOURCE`), концы строк LF (`CRLF_LFONLY`) — hexdump сохраняет строки; финальные
  LF убираются. Для отладочных сообщений ядро само добавляет имя функции
  (`CONFIG_LOG_FUNC_NAME_PREFIX_DBG=y` по умолчанию) — оставлено как есть.
- Санитизация как у ESP32, но без разбора ANSI: строгий UTF-8, CR удаляется (CRLF → LF),
  LF и таб сохраняются, прочие управляющие и битые последовательности — U+FFFD с
  схлопыванием серий; обрезка 512 Б по границе символа, `truncated=true`. Формат
  форматируется сначала в сырой буфер `CONFIG_ZEPHYR_LOG_SOURCE_RAW_MAX` (1024 Б), всё,
  что длиннее, — тоже `truncated`.
- Уровни: ERR/WRN/INF/DBG → error/warning/info/debug; сырые строки (`printk` через
  лог, `LOG_PRINTK`, `LOG_RAW`) — level null, module null. `generation` у STM32 — 0.
- `uptime_ms` — таймстемп сообщения (момент вызова `LOG_*`), не момент обработки;
  `seq` — момент попадания в кольцо (обработка потоком лога).
- Паника: флаг, `log_store_panic()`; дальше только счётчики и спинлок потерь store.
- Кольцо инициализирует сам модуль на `POST_KERNEL` 99 (`ZEPHYR_LOG_SOURCE_INIT_STORE`),
  backend до этого `is_ready = -EBUSY`. На плате поток лога опрашивает неготовые
  backend-ы, но сюда он придёт уже с готовым кольцом — ранние сообщения из deferred-буфера
  не теряются (отдельный захват до кольца не нужен).

## Ошибка ядра лога Zephyr: отчёт о потерях перестаёт приходить

`subsys/logging/log_core.c`, `z_impl_log_process()`:

```c
if ((dropped_pend || unordered_pend) &&
   (k_uptime_get() - last_failure_report) > CONFIG_LOG_FAILURE_REPORT_PERIOD) {
	...dropped_notify();
}
last_failure_report += CONFIG_LOG_FAILURE_REPORT_PERIOD;   /* на каждом вызове */
```

`last_failure_report` растёт на период при **каждом** вызове (каждом сообщении), а не
при отчёте. После N сообщений отчёт возможен только при uptime > N × период: при 1000 мс
и тысячах сообщений на старте `dropped()` backend-ов фактически больше не вызывается.
Обход без правки дерева — `CONFIG_LOG_FAILURE_REPORT_PERIOD=0` (сюита работает с ним;
для прошивки — нужен в `prj.conf`, решение интегратора). Кандидат на патч/issue в Zephyr
(перенести `+=` внутрь условия или присваивать `k_uptime_get()`).
