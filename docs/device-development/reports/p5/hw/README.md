# P5 — аппаратные проверки на плате B (J-Link)

Плата B: J-Link `000941000024`, консоль `/dev/cu.usbmodem5AE60208891`, CDC приложения —
USB serial `2037394C3543501200210047` (`/dev/cu.usbmodem11201`), стендовый MCUboot
recovery — `3543501200210047`, DHCP `192.168.88.13`. Плата A (ST-Link, сессия P3) не
затрагивалась: ни прошивки, ни сброса, ни открытия её портов, ни запросов.

Перед каждым первым запуском скрипта:

    grep -n "192.168.88.14\|002F002B\|STM32_Programmer_CLI\|21103\|21301" *.py

Находит одну строку — константу отказа `BOARD_A_REFUSED` в `board_b.py` (адрес и серийники
платы A отвергаются до открытия портов и до запросов); цепочка прошивки прерывается, если
найдено что-то ещё.

## Скрипты

| Скрипт | Что делает | К чему обращается |
|---|---|---|
| `board_b.py` | Общее: отказ от платы A, консоль с временем хоста и командами шелла с повтором, HTTP-сессия, сырой GET с разбором chunked, проверка по `openapi.json`, J-Link, порт CDC по точному серийнику, ping | только плата B |
| `run_image_b.py <workdir> <signed.bin> <с>` | Образ в slot0 через CDC recovery стендового MCUboot (порт — по точному серийнику `3543501200210047`, а не подстрокой: серийник CDC приложения оканчивается теми же цифрами), затем консоль | J-Link, консоль, CDC recovery платы B |
| `logs_b.py <сценарий> <префикс>` | Сценарии P5: `smoke`, `two-sources`, `wrap`, `boot`, `slow <мин>`, `stalled`, `export`, `uart`, `c6-reset <n>`, `stacks`; пишет `<префикс>.json` и `<префикс>.console.log` на одном времени | `192.168.88.13`, консоль, J-Link, CDC приложения |

Ручных действий владельца в P5 нет: C6 сбрасывается через EN из прошивки, STM32 — через
J-Link, медленный и зависший клиенты — скриптом.

## Журнал

### 1. Образ 1 (`7dddb9d1…`): прошивка и старт (`logs/01-*`)

`run_image_b.py`: recovery на `/dev/cu.usbmodem11201` через 1,7 с, загрузка 363 с, slot0
подтверждён. Старт: `Start main app` 2,03 с, конфигурация сети revision 8 за 5 634 мс, веб
11,15 с, DHCP `192.168.88.13` 14,2 с. Отказов нет. `coprocessor WifiInit failed` — flash C6
пуст (ожидаемо). На старте `boot 1 of 5 in a row shorter than 30 s` — прошивка сбрасывает
плату; сценарии со сбросом ждут uptime > 31 с.

### 2. smoke (`logs/02-smoke.*`)

Все четыре ответа проходят схему: `LogSources`, `Capabilities` (`esp32_logs` available при
транспорте down — владелец UART консоль), `CoprocessorStatus` (`state=failed`: C6 говорит

`has_more=true` — страница обрезана по байтам буфера 16 КиБ; порядок seq сохранён).
Замечено и разобрано ниже: `esp32 generation` 122 через 82 с, `dropped_count` 95 331,
страница 1 015 мс против 146 мс у статуса.

повреждена), потерянные байты — отдельный счётчик в `coproc status`.

### 4. Задержка страницы (`logs/04-page-latency.json`, `logs/05-page-ttfb.json`)

### 30. Владелец UART, образ 4 (`logs/31-uart.*`)

Переключения: bridge 11 мс, console 10 мс, flashing 11 мс, console 11 мс; маркеры `paused 191` →
`reset 192 «UART returned to the log»` → … в том же порядке. **Первая проба после 5 с чтения CDC
— снова HTTP `TimeoutError` (15 с), при этом ping прошёл (12,8 мс)**; следующая проба через 21 с и
остальные — HTTP 200. Это 3-й из 4 прогонов сценария `uart` (образы 3 и 4), в `bridge-load` не
повторяется ни разу: сеть отвечает, не отвечает HTTP-сервер. DTR в этом прогоне мост не включил —
см. п. 31.

Консоль этого прогона (`logs/31-uart.console.log`) показывает, что после 5 с чтения CDC система
надолго перестала выполнять вытесняемые потоки, а ICMP продолжал работать:

| Время хоста | Что в консоли |
|---|---|
| 3,8 с | `coproc mode bridge: 0 in 11 ms`, строки W5500 с временем платы 04:33–04:34 |
| 9,3 с | хост перестал читать CDC; HTTP-проба не открыла соединение за 15 с, ping 12,8 мс |
| 28–105 с | строки W5500 приходят раз в ~4 с, время платы в них идёт по 0,2 с на строку (04:41 → 04:56): вывод лога в консоль отстаёт, к 105 с отставание ~70 с |
| 105 с | скачок: строки с временем платы 06:06–06:09 |
| 111 с | `coproc status`: `dtr follow off` — команда `coproc dtr on` на плату так и не пришла (шелл консоли не читал ввод) |

Итог: в сценарии `uart` (3 из 4 прогонов) после того, как хост прочитал поток моста и перестал
читать, **поток лога, консольный шелл и HTTP-сервер голодают десятки секунд**, пока что-то с более
высоким приоритетом занимает процессор; ping (обработка ICMP в потоке RX сети) отвечает. В
`bridge-load` (хост читает в отдельном потоке, пробы HTTP идут непрерывно) не повторилось ни разу.
Причина не установлена; кандидаты — работа CDC ACM на системной очереди (`CONFIG_USBD_CDC_ACM_WORKQUEUE`
не задан, `sysworkq` кооперативный −1) при переполненном TX, переоткрытия сокета W5500 (−14).
Открытый пункт.

Кандидаты из кода `zephyr/subsys/usb/device_next/class/usbd_cdc_acm.c` (чтение кода, на плате не
подтверждено): вся работа CDC ACM идёт в системной очереди (`CONFIG_USBD_CDC_ACM_WORKQUEUE` не
задан, `sysworkq` кооперативный); `cdc_acm_tx_fifo_handler()` при неудачном выделении буфера
конечной точки (пул `USBD_CDC_ACM_BUF_POOL_SIZE` 512 Б, по 2 буфера на каждый из двух экземпляров
CDC в DT) перезапускает себя каждую 1 мс — ровно случай хоста, который не забирает IN-передачи;
`cdc_acm_irq_cb_handler()` ставит себя снова, пока TX включён и в FIFO есть место. Эксперимент
для P6 (там UART передаётся библиотеке через тот же путь): отдельная очередь CDC ACM
(`CONFIG_USBD_CDC_ACM_WORKQUEUE`) с вытесняемым приоритетом и повтор сценария `uart`.
