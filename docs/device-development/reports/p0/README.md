# Отчёт этапа P0 — стабильная основа

Критерий раздела 10: «20 холодных/тёплых стартов, 2 ч network/PSRAM smoke,
сохранение существующего I/O; зафиксированы layout C6 и бюджет staging; пустой
`sim`-набор проходит в CI». Этап закрывается только выполненным на плате с
приложенными логами.

**Статус: не закрыт.** Выполнено на плате с логами: 20 стартов (10 тёплых +
10 холодных, 20/20 до готовности), 2 ч network/PSRAM smoke (без сбросов и
зависаний), layout C6 и бюджет staging, `sim` в CI. **Не выполнено:
«сохранение существующего I/O»** — проверку реле и входов владелец решил
пропустить (2026-09-13). Этап не отмечен закрытым, пока владелец не решит
закрыть его без этой проверки или проверка не будет сделана.

## Находки

Не чинились — P0 измерительный. Варианты — у каждой находки.

1. **BUS FAULT в `w5500_rx` после сброса C6** — `fault-c6-reset/README.md`.
   Драйвер не ограничивает длину кадра из заголовка W5500; система
   останавливается (нет watchdog и `RESET_ON_FATAL_ERROR`).
2. **Транспорт ESP-Hosted не восстанавливается после сброса C6** без сброса
   STM32 — `02-c6-rollback.md`. Требование к P6.
3. **Состояние реле по умолчанию (`/api/relays/safe_state`) хранится, но не
   применяется.** `io_init()` читает его из настроек, в выводы оно не пишется
   (`write_relays_once` — мёртвый код). На старте реле выставляет Matter по
   StartUpOnOff: «Endpoint N On/off already set to new value». Серия стартов
   это подтверждает на плате: сохранённое `relay1=true, relay3=true`
   переживает сбросы, а `/api/relays/state` после старта — все `false`.
   **Решение владельца 2026-09-12: состояние по умолчанию управляется Matter
   (StartUpOnOff); эндпоинт `/api/relays/safe_state` и его логика удалены
   целиком** — в рабочем дереве, после серии тёплых стартов (замеры сделаны на
   образе с эндпоинтом). Проверка «состояние по умолчанию работает» делается
   через StartUpOnOff chip-tool'ом.
4. **Полярность реле инвертирована — подтверждено владельцем по светодиодам.**
   В DTS реле `GPIO_ACTIVE_LOW`, катушки через ULN2003 (высокий уровень на
   входе — катушка под током, светодиод XL-1608 параллельно катушке). При всех
   реле логически выключенных (REST `false`, Matter OnOff off) биты ODR
   PA5/PC4/PC5/PB2 = 1 и **все четыре светодиода горят** (владелец,
   2026-09-12). Следствия: логическое «выключено» — катушка под током и
   постоянное потребление; при каждом сбросе выводы уходят в Hi-Z, ULN2003
   закрывается, катушки отпускают на время загрузки (~3 с до инициализации
   GPIO) и снова притягиваются — два переключения каждого реле на сброс.
   Что это значит для нагрузки, зависит от того, на NO или NC она подключена.
   Варианты: `GPIO_ACTIVE_HIGH` в DTS платы (репозиторий `cedar_board_zephyr`) —
   тогда «выключено» без тока и сброс не переключает реле; либо оставить, если
   нагрузка сознательно на NC. Решает владелец.
   Нумерация закрыта схемой: OUTPUT1..4 = выводы 21/24/25/28 = PA5/PC4/PC5/PB2,
   расхождения на единицу нет. Какой OUTPUT на какое RLY — на проверке I/O.
5. **FRAM `mb85rsxx`** — RDID отвечает `04 7F 03 02`, драйвер отказывает в
   инициализации **на каждом старте: 20 из 20** (тёплые и холодные) плюс
   первый старт после прошивки. Не «иногда», а всегда — значит, не контакт и
   не питание при старте, а скорее несовпадение чипа с ожидаемым драйвером ID
   (или сам чип другой). Варианты: сверить маркировку установленной FRAM с
   таблицей ID драйвера; убрать узел из DTS, если FRAM не используется;
   добавить ID, если чип совместим. Кто пользуется FRAM в приложении — не
   выяснялось.
6. **HTTP под частым опросом.** Запросы с таймаутом 2 с раз в ~2,25 с на старте
   держали сервер без ответа 180 с (80 из 80 — таймаут), следующий запрос
   после остановки опроса прошёл. У сервера 4 клиентских слота и 10 с
   неактивности: брошенные соединения занимают его дольше, чем приходят новые.
   Это задача P2 («корректная уборка при abort»), не дефект старта;
   старт меряется последовательными запросами после первого ответа на ping.
8. **Файловый бэкенд настроек медленный и становится медленнее.** Все
   настройки, включая ключи Matter, живут в одном файле `/lfs/settings`
   (`CONFIG_SETTINGS_FILE`, до 128 строк). По коду `settings_file.c`:
   каждая загрузка с фильтром дубликатов для каждой строки просматривает весь
   остаток файла, каждая запись перед этим читает файл целиком ради проверки
   дубликата, уплотнение — только при 128 строках. Matter на каждом старте
   пишет RebootCount и другие счётчики, так что файл растёт от старта к
   старту. Измерено: чтение пяти ключей — ~0,58 с; Matter init в серии
   рос с 20,5 до 29,9 с. Переход на settings-registry (сделан по решению
   владельца) эту цену не снимает: реестр хранит ключи в том же файле через
   `settings_save_one`, но читает их один раз при старте, а не на каждый
   запрос. Варианты: поднять `CONFIG_SETTINGS_FILE_MAX_LINES` или перейти на
   бэкенд ZMS/NVS на отдельном разделе — решает владелец; перед этим измерить
   размер файла и рост за N стартов.
10. **Приём UART консоли теряет байты.** 6 одиночных байт на ~10,8 КиБ входящих
    команд за 2 ч smoke (115200, ST-LINK VCP). Отдельно при чтении C6 через мост
    CDC↔USART3 обрывались пакеты больше ~8 КиБ. Одна ли причина — не
    проверялось. Для веб-интерфейса неважно, для сервисной консоли и будущего
    `esp32-log-source` (P5) — да: потери надо считать, а не предполагать.
9. **Прочие ошибки лога на каждом старте**: `net_ethernet: Invalid MAC address
   for iface 1`, Matter `DNS-SD advertising not available` (известно,
   commissioning и discovery в P3), DHCP «more DNS servers than can be saved».

Один сброс, затем 150 с попеременно `GET /api/relays/safe_state` и
`GET /api/relays/state`, последовательно, с таймаутом 30 с. Все 440 запросов

причина, не проверено.

**Не проверялся — решение владельца 2026-09-13.** Не выполнены: каждое реле

## Изменения кода в этой сессии (решения владельца)

Все замеры выше — на образе `a59bdebd…`, до этих правок. Новый образ собран
(`-p always`, код возврата 0), но на плату не прошивался и не проверялся.

- Удалён `/api/relays/safe_state` и его логика: обработчик, ключи
  `/settings/relays/default/*`, тип `relays_def_state`, их чтение в
  `io_init()`, мёртвая `write_relays_once`.
- Код приложения обращается к настройкам только через settings-registry:
  MQTT — пять ключей `mqtt/*` в `mqtt_settings.c` (ошибка записи → 500,
  порт ограничен 0–65535); убраны мёртвая `warmup_settings_cb` и лишние
  `#include <zephyr/settings/settings.h>`. Старые ключи `/settings/mqtt/*`
  не переносятся. Закомментированный код не менялся.
