# BUS FAULT в `eth_w5500` после сброса ESP32-C6

Дата: 2026-09-12, чистый образ из `01-clean-build.md` (sha256 `a59bdebd…`).
Наблюдался один раз. Не чинился — P0 измерительный, решение за владельцем.

## Что произошло

Последовательность, шаг 2 (чтение загрузчика C6):

1. `wifi_ctrl init` — C6 в download mode.
2. Три `esptool read-flash` через мост CDC↔USART3, все оборвались
   (`Packet content transfer stopped`).
3. `wifi_ctrl reset` — импульс на EN C6, BOOT неактивен.
4. Через 14 с по часам STM32:

```
[00:03:13.112,000] <err> os: ***** BUS FAULT *****
[00:03:13.112,000] <err> os:   Precise data bus error
[00:03:13.112,000] <err> os:   BFAR Address: 0xc
[00:03:13.112,000] <err> os: r0/a1:  0x7016a850  r1/a2:  0x000000ea  r2/a3:  0x00000000
[00:03:13.112,000] <err> os: r3/a4:  0x000000ea r12/ip:  0x20000914 r14/lr:  0x0206201f
[00:03:13.112,000] <err> os: Faulting instruction address (r15/pc): 0x02062032
[00:03:13.112,000] <err> os: >>> ZEPHYR FATAL ERROR 25: Unknown error on CPU 0
[00:03:13.112,000] <err> os: Current thread: 0x20000a10 (eth_w5500)
[00:03:13.123,000] <err> os: Halting system
```

Система остановилась и так и осталась бы: `CONFIG_RESET_ON_FATAL_ERROR` не
задан, watchdog нет (решение владельца — позже). Плату перезапустил следующий
`-hardRst`. Полный вывод — `chain-output.log`; консоль —
`../c6-rollback/console-download-mode-3.log`.

Раньше в тот же день такой же `wifi_ctrl init` → чтение → `wifi_ctrl reset`
на предыдущем образе отказа не дал (плата отвечала ещё ~2 минуты, до
перепрошивки). Одно наблюдение из двух — не воспроизводимость.

## Где

`addr2line` по ELF этой сборки: PC `0x02062032` и LR `0x0206201f` —
`w5500_rx`, `zephyr/drivers/ethernet/eth_w5500.c:256` и `:268`, цикл
раскладки кадра по фрагментам:

```c
rx_len = sys_get_be16(header) - 2;            /* длина из буфера W5500 */
pkt = net_pkt_rx_alloc_with_buffer(ctx->iface, rx_len, NET_AF_UNSPEC, 0, ...);
pkt_buf = pkt->buffer;
read_len = rx_len;
do {
        frag_len = net_buf_tailroom(pkt_buf);  /* <- PC: pkt_buf == NULL */
        ...
        read_len -= frame_len;
        pkt_buf = pkt_buf->frags;
} while (read_len > 0);
```

Инструкция `ldr r2, [r6, #12]` при `r6 = pkt_buf->frags = NULL` даёт ровно
`BFAR 0xc`.

## Почему `pkt_buf` кончился раньше кадра

`net_pkt_rx_alloc_with_buffer` не обязан выделить `rx_len`:
`pkt_buffer_length()` (`subsys/net/ip/net_pkt.c:1165`) для `NET_AF_UNSPEC` на
Ethernet-интерфейсе ограничивает размер `MTU + NET_ETH_MAX_HDR_SIZE` и
возвращает `MIN(size, max_len)`. Драйвер же проверяет заголовок только снизу
(`<= 2` — ошибка) и не сравнивает `rx_len` ни с этим пределом, ни с
`Sn_RX_RSR` (`rx_buf_len`, прочитан строкой выше и дальше не используется).
Любое значение длины больше ~1518 — и цикл идёт за последний фрагмент.

Откуда взялась такая длина, не доказано. Совпадение по времени — сброс C6,
который висит на той же шине SPI2 (свой CS, общие SCK/MOSI/MISO), — делает
вероятной порчу чтения или рассинхронизацию указателя буфера W5500, но
отдельного измерения не было. `r1 = r3 = 0xea` в дампе — не длина кадра.

## Варианты — решает владелец

1. Принять как известный риск вместе с голоданием потока W5500 (тот же
   драйвер, тот же возврат до P8). Сброс C6 при работающем STM32 в
   эксплуатации будет — это штатный шаг обновления C6 в P6.
2. Локальный патч в `patches/` по образцу MMB: отбрасывать кадр, если
   `rx_len > rx_buf_len - 2` или больше `NET_ETH_MAX_FRAME_SIZE`, и
   переоткрывать сокет. Маленький, отправляется в апстрим отдельно.
3. Ждать #115626. PR переписывает `w5500_rx` и добавляет ровно эту проверку —
   `if (rx_len > rx_buf_len)` кадр отбрасывается (проверено по `gh pr diff`
   2026-09-12). Но PR открыт с 2026-08-07, ревью нет, и правит тот же файл,
   что наш патч MMB.
4. Отдельно от драйвера: `CONFIG_RESET_ON_FATAL_ERROR=y`, чтобы любой fault
   заканчивался перезагрузкой, а не остановкой. Меняет поведение при отказе,
   а не причину; пересекается с решением «watchdog позже».

Воспроизведение, если понадобится: `wifi_ctrl reset` в цикле при работающем
Ethernet, с захватом консоли.
