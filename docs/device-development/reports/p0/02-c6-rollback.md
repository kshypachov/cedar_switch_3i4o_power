# P0, шаг 2 — состояние otadata и rollback на ESP32-C6

Дата: 2026-09-12. Вход в P6: в какой слот писать обновление по UART и есть ли откат.

## Как читалось

Только `read-flash`, ничего не записывалось и не стиралось.

1. `wifi_ctrl init` в шелле STM32 — C6 в download mode (EN/BOOT).
2. `esptool 5.3.1 --chip esp32c6 -p <CDC платы, VID 0x2fe3> -b 115200
   --before no-reset --after no-reset read-flash <адрес> <размер> <файл>`.
3. `wifi_ctrl reset` — C6 в normal boot.

Сырые данные лежат рядом: `partition-table.bin` (`0x8000`, 3 КиБ),
`otadata.bin` (`0xd000`, 8 КиБ), `ota_0-head.bin` (`0x10000`, 256 Б),
`ota_1-head.bin` (`0x1d0000`, 256 Б), журнал `esptool.log`. Чип:
ESP32-C6FH4 (QFN32) rev v0.1, MAC `e4:b3:23:a6:9e:e0`.

Формат сверен с исходниками ESP-IDF 5.5.5, которой собран CP
(`CONFIG_IDF_INIT_VERSION="5.5.5"`): `esp_ota_select_entry_t` —
`ota_seq`, `seq_label[20]`, `ota_state`, `crc`, где `crc` — CRC32 только поля
`ota_seq` (`bootloader_common_ota_select_crc`, в `otatool.py` —
`binascii.crc32(pack('<I', seq), 0xFFFFFFFF)`); выбор слота —
`bootloader_utility_get_selected_boot_partition`.

## Включён ли rollback — не подтверждено на чипе

otadata на этот вопрос не отвечает: `VALID` с `seq=1` загрузчик ведёт одинаково
при любой настройке rollback. Ответ даёт только сам загрузчик. У локальной
сборки (`build/bootloader/bootloader.bin`, 22 176 Б, sha256 `f5564a2f…`) в
`config/sdkconfig.h` нет `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`, в
`sdkconfig:459` он «is not set». Сверить эту сборку с байтами `0x0` на чипе не
удалось: три попытки чтения загрузчика оборвались в мосту CDC↔USART3
(`Serial data stream stopped`, `Packet content transfer stopped`), при том что
8 КиБ otadata прочитались с первого раза. Повторять не стал — см. ниже, сброс
C6 во время работы STM32 закончился отказом.

Косвенно: `ota_1` пуст, значит OTA-обновление на этом чипе ни разу не
выполнялось, и `ota_state=VALID` записан не механизмом подтверждения после
OTA. Проверенного на чипе ответа нет.

## Что узнали попутно

- **Транспорт ESP-Hosted не восстанавливается после сброса C6 без сброса STM32.**
  После `wifi_ctrl reset` C6 загрузился и прислал `coprocessor priv event 34`,
  но `wifi scan` трижды за ~2 минуты ответил `Scan request failed`. После
  сброса STM32 scan сразу заработал. Для P6 это требование: после записи
  `coprocessor-updater` должен заново провести инициализацию транспорта, а
  проверка запуска C6 без неё всегда провалится.
- **Сброс C6 при работающем STM32 однажды уронил систему.** Второй раз, на
  чистом образе, через 14 с после `wifi_ctrl reset`: BUS FAULT в потоке
  `eth_w5500`, `w5500_rx`, разыменование NULL (`BFAR 0xc`), система
  остановлена. Разбор — `fault-c6-reset/README.md`.
- **Мост CDC↔USART3 теряет данные** на чтении больше ~8 КиБ за раз на 115200.
  Прошивка C6 из веба идёт мимо моста (esp-serial-flasher на USART3), но
  сервисную процедуру через USB это касается.

## Варианты для P6 — решает владелец

| Вариант | Как | Откат | Что нужно |
|---|---|---|---|
| А. Писать `ota_0` на месте | Стереть и записать `0x10000`, otadata не трогать | Нет. Отказ посреди записи — C6 не загружается, `recovery_required`, повтор записи по UART | Ничего сверх текущего; ROM loader доступен всегда, так что повтор возможен |
| Б. Писать `ota_1` и переключать otadata | Записать `0x1d0000`, проверить, затем записать `otadata` c `seq=2` (и CRC) | Ручной: `ota_0` остаётся целым, возврат — переписать otadata на `seq=1`/`3`. Автоматического отката нет, раз rollback выключен | Писать otadata самим (32 Б + CRC, две копии), чередовать слоты при следующих обновлениях, знать активный слот — читать otadata перед записью |
| В. Как Б, плюс включить rollback в CP | Пересобрать CP с `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`, прошить загрузчик один раз сервисно; новое приложение подтверждает себя после self-test | Автоматический, если новый образ не подтвердит себя | Меняет загрузчик C6 (сервисная прошивка через USB), подтверждение в CP firmware; раздел 8 сейчас выносит это за первую версию |

Вне зависимости от варианта: после записи STM32 должен переинициализировать
транспорт ESP-Hosted (см. выше), а адреса берутся из проверенной таблицы, не из
запроса.
