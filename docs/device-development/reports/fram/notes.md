# FRAM на SPI1: ошибка RDID и частота (2026-09-19)

Вопрос владельца: при старте в логе

```
mb85rsxx: invalid device ID: 04 7F 03 02
mb85rsxx: Failed to initialize device, RDID check failed (err -5)
```

— неправильно настроен DT?

## Микросхема

`04 7F 03 02` — правильный ответ RDID от **Fujitsu MB85RS64V** (даташит DS501-00015,
раздел RDID): производитель 04h, код продолжения 7Fh, первый байт изделия 03h
(плотность 00011b = 64 Кбит), второй 02h. 8 КиБ — совпадает с `size = <8192>` в DT
платы. Шина, CS (PB8) и режим SPI в порядке: ID приходит без искажений.

## Почему ошибка

Драйвер Zephyr `fujitsu,mb85rsxx` (`drivers/eeprom/eeprom_mb85rsxx.c`) принимал только
2-мегабитные MB85RS2MT и MB85RS2MTA (третий байт `0x20` по маске старших трёх бит или
`0x48`, четвёртый `0x03`). Частота к ошибке отношения не имеет: на любой частоте было бы
то же самое.

Одной строки в проверке ID мало. По даташиту READ и WRITE у MB85RS64V принимают
**16-битный адрес** («arbitrary 16 bits address… the 3-bit upper address bit is invalid»),
а драйвер всегда слал 24 бита. С исправленной только проверкой ID init прошёл бы, но
`WRITE 02 00 00 10 DD` записал бы `10 DD` по адресу 0, а каждое чтение возвращало бы
данные со сдвигом на байт.

Исправление — патч `patches/zephyr/eeprom_mb85rsxx-support-mb85rs64v.patch` (+23/−8,
урезан до минимума по просьбе владельца): принять ID MB85RS64V и слать 2 байта адреса
для микросхем до 512 Кбит (`size` ≤ 64 КиБ), 3 байта — для больших.

Альтернатива без правок дерева Zephyr (не выбрана, владелец попросил патч): штатный
драйвер `atmel,at25` — ID при init не проверяет, `address-width = <16>` поддерживает,
ожидание записи опрашивает WIP в RDSR (у FRAM он всегда 0). Оверлей:
`compatible = "atmel,at25"; address-width = <16>; pagesize = <64>; timeout = <1>;`
и `CONFIG_EEPROM_AT25=y`.

## Частота

В DT платы у `fram@1` стоит `spi-max-frequency = <60000000>`. SPI1 тактируется от PCLK2 =
160 МГц; `spi_stm32.c` берёт первый делитель-степень двойки, при котором частота не выше
заданной: 160 → 80 → **40 МГц**. Предел MB85RS64V по даташиту — **20 МГц**. Правильное
чтение ID при 40 МГц спецификацию не подтверждает: это один экземпляр при комнатной
температуре. Оверлей приложения теперь задаёт 20 МГц (PCLK2 / 8). NOR на той же шине не
затронут — делитель выставляется на каждое устройство.

## Кто пользуется FRAM

Никто в приложении. MAC берётся из I2C EEPROM по адресу 0x50
(`src/lib-init/net_init.c`); комментарий в оверлее, говоривший про MAC из FRAM, исправлен.

## Проверка

- Даташит: ID, 16-битный адрес, 20 МГц — подтверждены.
- Сборка проходит, в `zephyr.dts` у `fram@1` 20 МГц; `git apply --reverse --check` патча
  проходит, `west patch list` принимает `patches.yml`.
- **Плата 192.168.88.10, прошивка 1.1.3+17** (`9dac2d43…`, `~/Downloads/cedar-firmware/`;
  владелец поставил её через веб 2026-09-19 ~18:15, до подтверждения): в логе загрузки
  `mb85rsxx device ID read successfully: 04 7F 03 02` вместо ошибки. Шелл `eeprom` через
  telnet:
  - `eeprom size fram@1` — 8192; исходно по 0, 0x100, 0x0FF8, 0x1FF8 нули;
  - запись `de ad be ef 01 02 03 04` по 0x100 — Verify OK; чтение с 0xFC показывает её ровно
    на 0x100–0x107 (сдвига на байт нет), смещение 0 не изменилось;
  - запись по 0x1FF8 (конец памяти) и `a5 5a` по 0 — читаются обратно, 0x0FF8 не задет,
    0x100 цел;
  - после теста все три места заполнены нулями обратно (`eeprom fill`), как было.

  -ENOTSUP от шелла не было: буферы шелла дошли до DMA SPI1 без ошибок.
