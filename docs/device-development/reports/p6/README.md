## Первое измерение: flash C6 платы B через ROM loader (только чтение)

2026-09-14, `tests/esp_loader_flash_probe` (вызывает только `connect`, `read_mac`,
`flash_detect_size`, `flash_read`, `reset_target`; ни одной команды записи, стирания или
`FLASH_BEGIN`), образ `61c07f83…`, лог `hw/logs/01-c6-flash-probe-read-only.log`.
`init_flash_params` библиотеки перед чтением шлёт `SPI_ATTACH` и `SPI_SET_PARAMS` — это
настройка SPI в RAM C6, не запись во flash.

| Участок | Байт | Время | Результат |
|---|---:|---:|---|
| bootloader `0x0` | 4096 | 594 мс | все `0xFF` |
| partition table `0x8000` | 3072 | 418 мс | все `0xFF` |
| NVS `0x9000` | 256 | 39 мс | все `0xFF` |
| otadata[0] `0xd000`, otadata[1] `0xe000` | 64 + 64 | 13 + 13 мс | все `0xFF` |
| phy_init `0xf000` | 64 | 13 мс | все `0xFF` |
| `ota_0` `0x10000`, `ota_1` `0x1d0000` | 512 + 512 | 74 + 73 мс | все `0xFF` |

- Подключение 522 мс, target ESP32-C6, MAC `40:4c:ca:5c:46:f8`, flash 4 МБ (по ID микросхемы).
- **Flash C6 платы B пуст во всех участках, от которых зависит дизайн**: ни загрузчика, ни
  таблицы разделов, ни otadata, ни приложения, NVS не инициализирован. Решение №1 (Г) это
  покрывает: единый файл с `0x0` — единственный путь, при котором C6 загрузится.
- Чтение через ROM — 64 Б на команду, ≈6,9 КБ/с. Сверка записанного чтением всего образа
  (1,47 МБ) заняла бы ≈3,5 мин — проверка записи идёт по MD5 (`flash_finish`), не чтением.
- После `reset_target` образ завершился `PASS`; C6 возвращён в normal boot (без загрузчика
  ROM продолжит перезапускаться, как в P5).

## Дизайн (записан до кода; факты — `notes-design-inputs.md`)

### Формат и проверка файла
- **Один формат v1 — `raw_full_flash`**: файл `idf.py merge-bin` (raw), пишется с `0x0` целиком.
  `FirmwareImage`: `format="raw_full_flash"`, `format_version=null`, `kind="recovery_bundle"` (файл
  заменяет загрузчик и таблицу и стирает NVS C6 — ровно то, что контракт называет recovery), поэтому
  `acknowledge_recovery=true` обязателен (иначе `422 validation_failed`); фронтенд отправляет `true`
  с пояснением. `version` — `app_desc.version`; `partition_layout_id` — имя разметки из allowlist,
  которой совпала таблица (`cedar-c6-ota-4m-2x1792k`); `host_protocol` — значение профиля
  (`esp-hosted-mcu-3`), **с образом не сверяется** (решение №4 отложено); `signature_verified=null`;
  `allowed_methods=["uart"]`.
- Проверка — чистый потоковый разбор (файл подаётся кусками по порядку, без файлового I/O внутри):
  1. `[0, 0x8000)`: загрузчик — `0xE9`, `chip_id=13`, сегменты в пределах, checksum, SHA-256
     (`hash_appended=1` обязателен), `bootloader_desc` magic 80; остаток до `0x8000` — `0xFF`.
  2. `[0x8000, 0x9000)`: таблица — записи `0x50AA`, MD5-запись совпадает (MD5 своей реализацией:
     в сборке нет PSA MD5), разметка **точно** равна allowlist; остаток — `0xFF`.
  3. `[0x9000, 0x10000)`: всё `0xFF` (NVS стёрт, otadata пуст → загрузчик выберет `ota_0`, phy_init не используется).
  4. `[0x10000, конец)`: приложение — `0xE9`, `chip_id=13`, сегменты, checksum, SHA-256,
     `app_desc` magic; конец приложения = конец файла; конец ≤ `0x1d0000` (начало `ota_1`).
  - Коды: чужой `chip_id` в загрузчике или приложении — `unsupported_target`; таблица не из allowlist
    — `incompatible_firmware`; остальное (голый app `.bin`, обрезанный, мусор в промежутках, неверный
    SHA/MD5/checksum) — `invalid_image` с понятным `message`. SHA-256 всего файла сверяется с
    объявленным в `createUpload` в том же проходе.
- `limits.upload_max_bytes` = `0x1d0000` (1 900 544): больше в слот не поместится; `createUpload`
  с большим `size_bytes` — `413 payload_too_large`. `firmware_formats=["raw_full_flash"]`.

### firmware-store
- Файлы `/lfs/firmware/upload.bin` и `/lfs/firmware/upload.meta` (двоичная запись с версией и CRC32);
  имя на ФС — только эти, клиентское имя — поле метаданных.
- Кусок: HTTP-обработчик проверяет offset/размер и копирует байты в буфер хранилища (один кусок за
  раз), задача `upload_chunk` на рабочем потоке пишет, `fs_sync` файла, затем метаданные с новым
  `received_bytes` и их `fs_sync`; только после этого задача `succeeded`.
- Старт: метаданные повреждены → удалить оба файла; файл длиннее `received_bytes` → обрезать до него
  (кусок записан, метаданные нет); короче → `received_bytes` = размер файла. Посторонние файлы в
  каталоге удаляются.
- Квота: LittleFS не резервирует блоки под файл. Устройство проверяет `fs_statvfs` на весь недостающий
  объём плюс запас (`CONFIG_FIRMWARE_STORE_RESERVE_KIB`) при `createUpload` и перед каждым куском;
  `storage_full` при создании — до первого байта. Честная граница: другой писатель `/lfs` (settings)
  между проверками может занять место — тогда отказ придёт задачей куска, не молча.
- Истечение: 24 ч uptime без активности; активная установка блокирует истечение и `DELETE` (`409 busy`).
- Проверка (`verifyUpload`) — задача, читает файл кусками в разбор выше; отменяема (`cancelJob`).

### esp-loader-adapter
- Шов для фейка — таблица функций над `esp_loader_*` (init/deinit порта, connect, target,
  flash_start/write/finish с MD5, reset_target, change_rate). Порядок: `coprocessor_manager_set_mode(FLASHING)`
  → `esp_loader_init_serial` (callback USART3 и EN/BOOT у библиотеки) → connect с попытками →
  проверка ESP32-C6 → `flash_start(0x0, размер)` (ROM стирает под записью) → блоки → `flash_finish`
  (MD5) → `reset_target` (normal boot) → `esp_loader_deinit` → EN/BOOT сразу в неактивное состояние →
  `set_mode(CONSOLE)`. Уборка — при любом исходе, в том числе отказе посреди записи.
- Адрес записи всегда `0x0`, размер — размер проверенного файла; ни stub, ни deflate, ни eFuse,
  ни Secure Download Mode в первой версии; скорость выше 115200 — после приёмки (решение №7).

### coprocessor-updater
- Задача `coprocessor_update`, фазы контракта: `preflight` → `entering_bootloader` → `begin` → `writing`
  → `verifying` → `reconnecting` → `health_check` → `complete` (`activating`/`confirming` не используются).
  Отменяема до `begin`; после — `cancellable=false`, `cancelJob` → `409 invalid_state`.
- Отказы в HTTP до задачи: `method="ota"` → `503`; не Ethernet → `409 ethernet_required`; upload не
  `ready` → `409 invalid_state`; UART у моста → `409 busy`; уже идёт установка → `409 busy`.
  **Состояние C6 (`offline`/`failed`) обновление не блокирует** — это путь первой прошивки и
  восстановления.
- Журнал `/lfs/firmware/update.journal` (через платформу, в sim — RAM): пишется при старте и на
  смене фаз, итог — `last_update`. На старте STM32 незавершённый журнал → `last_update.state=interrupted`,
  `recovery_required` = фаза дошла до `begin`; никакого продолжения, повтор — новым запросом.
- Health check (решение №2 (а)): после `reset_target` и возврата UART консоли — ранний признак по
  UART (строки загрузчика ESP-IDF и приложения в esp32-log-source) и затем повторная инициализация
  ESP-Hosted патчем драйвера (версия прошивки, для готового Wi-Fi-устройства — WifiInit/Start).
  `succeeded` — только с подтверждённой версией; иначе `failed` + `recovery_required`. Для Wi-Fi-
  устройства, не готового с момента старта STM32 (плата B), интерфейс поднимется только после
  перезагрузки STM32 — это записывается в итоге задачи, не скрывается (`notes-design-inputs.md`).
- Мост и DTR: переход в `flashing` при UART у моста отказывает (`-EBUSY` менеджера P5); опрос DTR
  включает мост только из `console`, поэтому во время записи не срабатывает.

### HTTP
- `PUT …/data`: новый флаг маршрута web-api — тело `application/octet-stream` до
  `CONFIG_WEB_API_OCTET_BODY_MAX` (16 384), иной тип — 415, больше — 413, пустое — 422; буфер тела
  контекста — максимум из JSON и октетного лимита.
- `ethernet_required`: локальный адрес соединения (`zsock_getsockname`) → `net_if_ipv4_addr_lookup`
  → интерфейс сравнивается с Ethernet платы.
- Все 7 операций P6 → устройство обслуживает 35 из 35.

  запись в `patches/patches.yml` и строка в `patches/README.md`; подробности —

  готово с загрузки STM32 (случай платы B)** — состояние устройства ядра не трогается.
- **Применён к общему дереву zephyr 2026-09-14 10:07:44 +0300** (по решению владельца «сразу после
  проверки»). Проверено: `git apply --check` чисто, прочие строки `git status`/`diff --stat` дерева не

- Известные ограничения: очередь TX при перезапуске не сбрасывается; ожидающий scan не будится

`modules/firmware-store` (README: жизненный цикл, восстановление, потоки, errno → контракт),
`tests/firmware_store`, корпус `tests/fixtures/esp32/firmware/` (генератор, независимая проверка
на Python `fwimage.py`, 12 синтетических `.bin` 808 КБ); `notes-firmware-store.md`.

**Медленный приём файла через веб (2026-09-14, после приёмки; найдено по жалобе владельца).** Загрузка
1,47 МБ шла ~1,6 КБ/с (медиана 10,4 с на кусок 16 КБ), в логе на каждый кусок
`fs: failed to unlink path (-2)`. Причины в модуле:
- `write_chunk()` на каждом куске звал `room_for()` → `fs_statvfs()`; у LittleFS это `lfs_fs_size()` —
  обход всех блоков всех файлов (`lfs_fs_traverse_`, CTZ-списки), по SPI NOR в режиме опроса. Кусок
  становился дороже по мере роста образа — квадратичная стоимость загрузки. **Решение владельца:
  свободное место спрашивается один раз при создании загрузки** (размер известен из запроса); место,
  занятое другими во время приёма, по-прежнему кончается `-ENOSPC` от самой LittleFS → `storage_full`.
- `write_meta()` перед записью метаданных делал `unlink` несуществующего временного файла; наш код
  считал `-ENOENT` нормой, но `fs_unlink()` Zephyr пишет `LOG_ERR` на любой отказ. Лишний `unlink`
  убран — `FS_O_TRUNC` и так обнуляет остаток (в пути отказа `unlink` остался: там файл есть).
- `test_storage_full_at_commit` переписан: чужой файл заполняет том, пока свободно меньше куска, и
  отказ приходит от LittleFS. `tests/firmware_store` — 78 из 78 (docker `cedar-sim-tests:1`,
  native_sim/native/64). Мутации для правки не прогонялись; на плате не проверено.

**Что ещё замедляет приём (разбор кода, не измерено на плате).** Медиана 10,4 с измерена со старым
`statvfs` и, вероятно, в основном им и объясняется; после правки оценка ~1 с на кусок 16 КБ. Остаток:
1. **Запись в firmware-store, ~0,4–0,6 с на кусок.** Файл открывается заново на каждый кусок
   (`firmware_store.c`, `write_chunk`) — LittleFS копирует неполный хвостовой блок в новый
   (`lfs.c:2938–2979`); `struct meta` ≈920 Б (`filename[513]`) не встраивается в каталог (предел 512,
   `lfs.c:4353–4360`) — `write_meta` каждый раз берёт и стирает блок; 4 коммита каталога на кусок
   (sync файла, создание tmp, sync tmp, rename) и уплотнение раз в 3–4 куска; стирание сектора ждёт
   `SPI_NOR_SLEEP_ERASE_MS=50` (`spi_nor.c`). ≈6–7 стираний на кусок. Варианты: держать файл образа
   открытым между кусками (только `fs_sync`); метаданные раз в N кусков или ≤512 Б (`recover()` уже
   сверяет размер файла с `received`); кусок 64 КБ (постоянные затраты ÷4, ОЗУ под `staging`).
2. **Фронтенд, ~0,3–0,7 с на кусок.** `waitJob` куска: сразу GET, дальше `FIRMWARE_POLL_MS=500`
   (`CoprocessorUpdateScreen.tsx`); лишний `getUpload` после каждого задания (`uploader.ts`);
   `MAX_IN_FLIGHT=2` (`client.ts`) делится с опросом статуса. Варианты: опрос задания куска 100–150 мс,
   `received = offset + len` без GET при `succeeded`.
3. **Приём Ethernet — не проверено.** Буфер приёма сокета 0 W5500 драйвер не задаёт (заводские 2 КБ,
   ~1 кадр); один кадр на прерывание RECV (~8 SPI-транзакций и занятое ожидание команды); окно TCP
   Zephyr ~10,9 КБ — при потерях RTO. Вариант: буфер сокета 0 16 КБ (правка драйвера — через патч).
4. **HTTP-сервер, десятки мс.** `HTTP_SERVER_CLIENT_BUFFER_SIZE=256`: тело 16 КБ — ≥64 цикла
   recv/разбора на кооперативном потоке. Вариант: 1460–2048 (ОЗУ × 4 клиента).
5. Не виновато: задержка ACK, пул `NET_BUF`, очередь `web_v1_jobs` (конкурентов при загрузке нет),
   логи (после правки на кусок ничего), обход ФС аллокатором (~1 раз за загрузку).
Порядок: замерить загрузку на новом образе (`upload_b.py`: `put_ms` и `job_ms` раздельно); если PUT
16 КБ > ~100 мс — сначала буфер W5500, иначе пункты 1 и 2.

## Нулевой шаг на плате: узел `espressif,esp-loader` в приложении

- **Первый старт с узлом повесил плату B** (образ `72378936…`, `hw/logs/02-step0-boot-hang.log`):
  консоль молчит после 7,7 с, `Start main app` нет, HTTP за 90 с не поднялся, ping 3/3 потерян.
  Причина по коду: init устройства esp-loader (POST_KERNEL) вызывает `tty_init()` + `tty_set_rx_buf()`
  — callback `tty_uart_isr` на USART3 и **включённое прерывание приёма**, а читателя нет до
  `coprocessor_service_start()` в `main()`. ROM-поток пустого C6 (11 КБ/с) заполняет кольцо приёма
  512 Б, и `uart_rx_handle()` на каждый выброшенный байт делает `tty_write(tty, "~", 1)` **из
  прерывания** с `tx_timeout = K_FOREVER` в кольцо передачи 512 Б, которое тоже никто не
  опустошает, — запись в ISR ждёт вечно (`zephyr/subsys/console/tty.c`). Попутно «~» уходят в C6.
  Исправление: узел `esp_loader0` помечен `zephyr,deferred-init` (binding включает `base.yaml`,
  `DEVICE_DT_INST_DEFINE` берёт флаг из DT) — ядро не вызывает init устройства при старте, USART3 до
  консоли никто не трогает. Выключать прерывания `SYS_INIT`-ом на следующем приоритете отвергнуто:
  на том же уровне POST_KERNEL 50 стоит init ESP-Hosted, который ждёт boot event до секунды, —
  окно, в котором ROM-поток успевает заполнить кольца. Порт библиотеки инициализирует
  esp-loader-adapter сам, в `flashing`, непосредственно перед connect, и освобождает `deinit` сразу
  после записи; `device_is_ready()` этого устройства всегда false и не проверяется.
- **С `zephyr,deferred-init` старт нормальный** (образ `d20d6321…`, `hw/logs/03-step0-deferred-init.log`):
  `Start main app` 1,93 с, DHCP `192.168.88.13` 15,7 с; HTTP и вход работают; `/coprocessor/status`,
  `/logs/sources`, `/capabilities` — схемы чистые; `uart_mode=console`, `state=failed` (C6 говорит по
  UART, транспорта нет); кольцо ESP32 принимает ROM-поток (`invalid header: 0xffffffff`, generation
  растёт от сбросов C6 сторожевым таймером); `coproc status` отвечает. **Не проверено**: сброс C6
  через `wifi_ctrl reset` — консоль потеряла `_` (`wifictrl reset`), команда не выполнилась; рост
  generation 78→86 за это время — собственные сбросы пустого C6. Проверка сброса повторяется в шаге 2
  (через telnet или с подтверждением ответа).
- Первая сборка с узлом не слинковалась: порт esp-serial-flasher зовёт `tty_init/read/write`, а
  `subsys/console` компилирует `tty.c` только с `CONFIG_CONSOLE_GETCHAR` (библиотека выбирает лишь
