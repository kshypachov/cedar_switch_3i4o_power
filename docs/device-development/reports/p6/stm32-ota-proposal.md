# Проект: обновление прошивки STM32 через веб (слот 2 на SPI NOR, обмен в MCUboot)

**Статус: проект, 2026-09-14.** Задача владельца: «Разработай процедуру обновления прошивки через
веб интерфейс. Чтобы прошивка записывалась в OTA SLOT 2 а MCUBOOT выполнял обмен слотами при
запуске. Дополнительный скрач слот можешь выделить на SPI FLASH». Код не писался, на плате ничего
не делалось. Решения владельца — в конце.

«Слот 2» здесь — `slot1_partition` (`image-1`, вторичный слот MCUboot).

### Хватит ли scratch 64 КБ

`boot_slots_compatible()` (`swap_scratch.c:283`) набирает участки одинакового размера из обоих слотов
(16 × 4 КБ слота 1 = 1 × 64 КБ слота 2) и отказывает, только если участок **больше** scratch
(`sz0 > scratch_sz`) — 64 КБ проходят. Трейлер scratch код учитывает: последний участок копируется
короче (`swap_scratch.c:739–741`), а максимальный размер образа уменьшается
(`app_max_size_adjust_to_trailer`). По коду увеличивать scratch не нужно; окончательно — по шагу 0
на плате. Переводить MCUboot на страницы 4 КБ не предлагаю: 1024 участка вместо 64 — это в 16 раз
больше стираний scratch и записей статуса за обмен, и ровно предел `BOOT_MAX_IMG_SECTORS`.

## Процедура

1. **Приём.** `POST /firmware/uploads`, как у ESP32. Сервер по первому куску узнаёт заголовок MCUboot
   (`0x96f3b83d`) → `target=stm32u585`, `format=mcuboot_image`. Данные идут **сразу в слот 2**
   через `flash_img` (`stream_flash`, стирание по ходу), не в `/lfs`: `firmware-store` рассчитан на
   образы ESP до 1,9 МБ, а промежуточный файл удваивает запись 1,4 МБ на медленную SPI NOR.
   - При создании: стереть **последние 64 КБ** слота 2. Трейлер ~49 КБ (1024 × 3 × 16 Б статуса плюс
     magic и флаги) — в разметке приложения это 13 последних секторов по 4 КБ, а 64 КБ совпадают с
     последним сектором MCUboot. Там остаются magic и `image_ok` прошлого `boot_request_upgrade`.
   - На первом куске: magic, `hdr_size`, `img_size` + TLV ≤ максимума образа, флаги, адрес загрузки.
   - После каждого куска — сброс буфера `stream_flash`, затем смещение пишется в журнал `/lfs`
     (одна маленькая запись на кусок); `received_bytes` = записано во flash и в журнале. Так
     сохраняется правило контракта (`api-contract.md:255`: устойчивое смещение после сбоя).
   - Одна активная загрузка на оба target: общий `spi1` и worker; установка ESP32 и настройка сети
     конфликтуют с ней (`409 busy`).
   - Поток записи вытесняемый и уступает процессор (правило владельца): стирание сектора 4 КБ на
     `spi1` занимает шину на ~50–100 мс, на образ 1,4 МБ таких ~350 — LittleFS и настройки ждут.
2. **Проверка** (`verify`): SHA-256 всего файла по слоту 2 против значения из `create`; разбор TLV —
   SHA-256 заголовка и тела совпадает с TLV (ту же проверку сделает MCUboot). Подписи нет →
   `signature_verified=null`.
3. **Установка** (`POST /system/updates {upload_id}` → задача `system_update`):
   `boot_request_upgrade(BOOT_UPGRADE_TEST)` (флаг в трейлере слота 2), запись журнала в `/lfs`
   (версия, sha256, «ожидает обмена»), ответ `202`, перезапуск через 1–2 с (ответ и опрос успевают).
4. **MCUboot при старте:** хук BBRAM → `boot_go`: тип TEST → проверка хеша слота 2 → обмен через
   scratch участками по 64 КБ (≈23 участка на образ 1,42 МБ плюс трейлер). Статус пишется в трейлер и
   scratch, после обрыва питания обмен продолжается с места. Длительность — измерить на шаге 0.
5. **Новое приложение:** видит неподтверждённый образ (`boot_is_img_confirmed()`) → самопроверка:
   настройки загружены, веб-API отвечает, сеть поднята (Ethernet или Wi-Fi), Matter стартовал,
   N секунд без отказа (предлагаю 60) → подтверждение. Задача получает `succeeded` только после
   подтверждения; журнал переживает перезапуски, как у `coprocessor-updater`.
6. **Подтверждение** — решение Д2:
   - (а) BBRAM + повторный перезапуск (хук уже есть): без правок zephyr, но нужен второй перезапуск,
     и если BBRAM без батарейки, пропадание питания до него откатит прошивку;
   - (б) `boot_write_img_confirmed()` из приложения: один байт `image_ok` в трейлер слота 1 на
     OCTOSPI, откуда выполняется код, — нужен `FLASH_STM32_OSPI_XIP`. Только запись страницы, без
     стирания; прерывания замаскированы на миллисекунды. Сразу и без перезапуска. **Рекомендую (б).**
7. **Откат.** Не подтвердился до следующего сброса → MCUboot возвращает старую прошивку (второй
   обмен той же длительности), задача — `rolled_back`. Зависание без сброса отката не вызывает →
   нужен IWDG (Д4). Программно запущенный IWDG STM32 после любого сброса выключен (включённым после
   сброса его делает только option byte аппаратного сторожа), поэтому обмен в MCUboot он не
   прерывает и перепрошивать MCUboot ради него не нужно. Оговорка: образ, зависший **до** запуска
   IWDG, не откатится — запускать как можно раньше (`SYS_INIT` на `PRE_KERNEL`).
8. **Статус:** версия и sha256 работающей прошивки, подтверждена ли, состояние слота 2
   (пусто / загружено / ожидает обмена / откат), итог последнего обновления.

## Что меняется

- **Контракт и `openapi`:** `target=stm32u585`, `format=mcuboot_image`, лимит размера на target в
  capabilities, задача `system_update` с фазами `requesting → rebooting → swapping → self_test →
  confirmed | rolled_back`, статус прошивки, флаг `features.stm32_update`; mock, экран «Прошивка»,
  i18n, тесты.
- **Модули:** второй приёмник в `firmware-store` (flash area рядом с файлом); валидатор заголовка
  и TLV MCUboot (тесты native_sim, фикстуры из `imgtool`); `system-updater` (журнал, запрос, самопроверка,
  подтверждение, сверка после старта) по образцу `coprocessor-updater`; связка платы.
- **Сборка:** версия образа из `CONFIG_MCUBOOT_IMGTOOL_SIGN_VERSION` (сейчас у всех 0.0.0+0 — отличить
  прошивки и запретить понижение нельзя); проверка, что `--align 1` не расходится с
  `BOOT_MAX_ALIGN=16` при расчёте трейлера.
- **`prj.conf`:** `CONFIG_FLASH_LOG_LEVEL_DBG=y` (строка 274) перекрывает `OFF` (строка 13). Для
  Д2 (б) это **обязательно**, а не уборка: в `aliro_reader` записано «Flash-driver log calls run
  from QSPI-resident code → hard-fault» — вызов `LOG_*` драйвера OSPI, пока отображение памяти
  снято, а код выполняется из XIP; `boot_write_img_confirmed()` идёт ровно этим путём. Убрать DBG
  до работ.
- **Драйвер XIP** (если Д2 = б): оформить правку из общего дерева в `patches/zephyr/`. Проверено:
  у `slot0_partition` в DTS платы (`…_ext_flash_app.dts:64`) нет `read-only`, flash map запись
  не запретит.

   64 КБ и хуки PSRAM/ICACHE после обмена. Тестовый образ — с другой версией
   (`CONFIG_MCUBOOT_IMGTOOL_SIGN_VERSION`, например `0.0.1`) и отличимой строкой при старте: у всех
   сборок `0.0.0+0`, иначе по баннеру и `image list` не видно, что обмен произошёл.
   **Результат (2026-09-14 18:36–19:05, плата B, `hw/README.md` строка 23):** обмен работает на
   текущей разметке без изменений DT. Загрузка в слот 2 через recovery 305 с; обмен образа 1,42 МБ
   через scratch 64 КБ — **~34 с** (с 3,4 с после сброса до 37,4 с, перед ним ~2,9 с проверка хеша);
   сброс без подтверждения — возврат той же длительности, прежний хеш в слоте 1; сброс через J-Link
   на 12-й секунде обмена — MCUboot продолжил с места и завершил. Для процедуры: перезапуск на
   обмен занимает ~40 с до старта приложения (UI должен ждать не меньше ~60 с); в стендовом MCUboot
   recovery отвечает только после обмена; `image test` через recovery идёт дольше 5 с (MCUboot
   проверяет хеши обоих слотов).

## Решения владельца

Приняты 2026-09-14 (~18:30):

- **Д1:** отдельный этап (новый worktree после закрытия P6).
- **Д2/Д5:** новая прошивка подтверждает себя сама, **если проработала 20 минут без падения**;
  плюс **консольная команда немедленного подтверждения**. Способ записи подтверждения (XIP-драйвер
  или BBRAM) владелец не выбирал — в проекте остаётся рекомендация XIP. Следствие: сброс в первые
  20 минут (в том числе штатный, по питанию) откатывает прошивку — это надо показывать в UI.
- **Д3:** пока без подписи.
- **Д8:** шаг 0 на плате B — сейчас (тест Apple Home прерывается).
