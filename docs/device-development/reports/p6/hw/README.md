# P6 — аппаратные проверки на плате B

Только плата B: J-Link `000941000024`, консоль `/dev/cu.usbmodem5AE60208891`, CDC приложения
`2037394C3543501200210047`, DHCP `192.168.88.13`. Плата A (ST-Link, сессия P3) не затрагивается:
`board_b.py` отвергает её адрес и серийники до открытия портов; перед первым запуском нового скрипта
`grep -n "192.168.88.14\|002F002B\|STM32_Programmer_CLI\|21103\|21301" *.py` находит только
`BOARD_A_REFUSED`.

C6 платы B записывается **только** приёмочным прогоном через веб (решение владельца): ни один
скрипт здесь не вызывает `startCoprocessorUpdate` (`upload_b.py` отказывает до запроса).

## Скрипты

| Скрипт | Что делает |
|---|---|
| `board_b.py` | Общее для всех: консоль с часами хоста, HTTP-сессия, J-Link, проверка схем (копия P5) |
| `run_image_b.py <workdir> <zephyr.signed.bin> <с>` | Образ в slot0 через CDC recovery стендового MCUboot, лог старта (копия P5) |
| `step0_b.py <префикс>` | Нулевой шаг: старт приложения с узлом esp-loader, схемы статусов, кольцо ESP32, `coproc status` |
| `upload_b.py upload\|stall\|corpus\|protocol\|reset …` | Шаг 1: загрузка и проверка файлов, отказы протокола, задержки HTTP при записи кусков, сброс STM32 посреди загрузки |

Образ C6 для загрузки берётся вне репозитория (scratchpad, `notes-design-inputs.md`): Wi-Fi CP
`750cb58e…` (1 468 176 Б), OT CP `5bbe0d27…` (869 056 Б); синтетический корпус —
`tests/fixtures/esp32/firmware`.

### Зависание в `entering_bootloader` (попытка 1 приёмки, 13:10)

- После `install job_0000005c: preflight` и через 3,3 с `entering_bootloader` консоль не выдала ни строки
  (ни `connected to the ESP32-C6 ROM loader`, ни сообщений W5500, ни потока лога); ping 100 % потерь.
  Остановилось всё, включая поток лога, — это уровень прерываний, а не один зависший поток.
- Объяснение по коду: `esp_loader_init_serial()` включает приём USART3 с обработчиком `tty`, у которого
  до первой записи библиотеки бесконечный `tx_timeout`; при полном кольце 512 Б обработчик пишет «~» из
  прерывания и ждёт вечно. Пустой C6 в этот момент ещё печатает ROM-цикл (~11 КБ/с), пока `connect`
  не удержит EN; достаточно ~50 мс вытеснения рабочего потока в этом окне — кооперативный поток W5500
  ждёт ~200 мс при каждом переоткрытии сокета (16 в минуту). `coproc loader` в 12:40 прошёл, потому что
  не попал в окно. То же окно есть после `reset_target`, пока порт ещё не освобождён.
- **Гипотеза владельца, не исключена:** C6 в загрузчике мешает на общей шине SPI2 (W5500 + ESP-Hosted).
  Против неё как причины полной остановки: зависшая SPI-транзакция остановила бы потоки W5500/ESP-Hosted,
  но не поток лога; сбросы пустого C6 сторожевым таймером (~раз в 0,65 с) полтора часа систему не
  вешали. Для фазы записи (C6 минутами в загрузчике) она остаётся открытой. Если зависание повторится —
  до сброса остановить ядро через J-Link и снять регистры и стек (PC в `tty`-ISR или в SPI/GPIO).
- Исправление в связке платы (модули не менялись): перед инициализацией порта C6 ставится в ROM download
  mode (`op_reset(download)`: короткий баннер, затем тишина); `reset_target` библиотеки только отмечает
  нужную обычную загрузку, а EN отпускается в `lines_idle()` после `port_deinit`.

### Переполнение стека `main` при непустом `/lfs/firmware` (12:26)

- `coprocessor_service_start()` выполняется на потоке `main` (стек 2048 Б): `psa_crypto_init()`
  хранилища, восстановление недокачанного upload (обрезка файла, перезапись метаданных на LittleFS) и
  чтение журнала updater. Образ шага 1 стартовал, потому что каталог был пуст; после прерванного
  сценария в нём лежал upload — путь восстановления на плате выполнился впервые и переполнил стек.
- Исправление: `CONFIG_MAIN_STACK_SIZE` 2048 → 4096 (комментарий в `prj.conf`); после старта снять
  фактический запас стека `main` (`kernel thread stacks`) и записать.
