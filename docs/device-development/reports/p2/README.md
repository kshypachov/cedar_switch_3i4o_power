# Отчёт этапа P2 — web shell и доступ

Критерий раздела 10: «UI работает офлайн, 2 клиента, нет обхода авторизации
через legacy, корректная уборка при abort». Раздел 12 добавляет sim-наборы для
`web-auth`, `web-api`, `web-assets` и аппаратные строки: задержка KDF на
реальном CPU, 2–4 клиента, p95 статусных запросов.

**Статус: выполнен локально и на плате, закрыть после прогона CI на GitHub.**
Workflow с новой задачей `frontend` в этой сессии не запускался — push делает
владелец.

## Замер сервера Zephyr до проектирования

`http-server-behaviour/` — сюита на native_sim против сервера этого дерева
(ревизия `b6a5e6e8aa90`). Каждое наблюдение изменило дизайн:

| Наблюдение | Решение |
|---|---|
| A. Ответ 204 уходит с `Transfer-Encoding: chunked` и терминатором `0\r\n\r\n`; строка статуса без reason phrase | 204 и 304 — с `Connection: close`; включён `COMPLETE_STATUS_PHRASES` |
| B. Второй клиент на ресурсе, где первый досылает тело, получает `409 Conflict` без тела, соединение закрывается | ресурс на каждый путь API; фронтенд повторяет голый 409 |
| C. Закрытие посреди тела → ABORTED за < 300 мс, ресурс свободен | контекст освобождается по ABORTED/COMPLETE |
| D. Застрявший клиент держит ресурс до таймаута неактивности | задокументировано; на плате — 10,2 с |
| E. При `MAX_HEADER_LEN=32` (значение платы) Cookie и CSRF молча отбрасываются | 256; отброшенный заголовок — 422 |
| F. Wildcard-ресурсы перебираются по имени, побеждает первый | ресурсы пронумерованы в порядке сопоставления |

Первый образ считал PBKDF2 (10000 итераций) прямо в потоке HTTP-сервера.

Выводы:

- Цель раздела 9 (p95 < 250 мс) выполнена для одного и двух клиентов, **для
  четырёх — нет**: сервер однопоточный, запросы ждут друг друга.
- `/` медленнее legacy-статики P0 (53 / 56 мс): теперь это динамический ответ
  с ETag, CSP и ещё семью заголовками. Время растёт с числом заголовков

  подтверждённая захватом трафика.**
- p95 1,09 с — артефакт клиента, который шлёт `Connection: close` и заставляет
  устройство закрывать соединение первым; первая серия `hw/logs/06` снята так же
  (там же 3 отказа соединения при 4 клиентах). Браузеры держат соединения,
  curl закрывает сам.

## Мутации

Каждая мутация — одно решение реализации, сломанное по отдельности; набор
прогоняется, файл восстанавливается. Мутация, после которой не собирается код,
не засчитывается пойманной.

### Фронтенд и Python (24)

Первый прогон: 20 пойманы, 4 выжили. Три выживших указали на пробелы в тестах,
которые закрыты, и повторно пойманы:

| Мутация | Пробел | Закрыт |
|---|---|---|
| `ui-poll-never-stops` — опрос недоступного ресурса не останавливается | тест считал запросы до первого повторного интервала | время проматывается на 16 с, недоступные ресурсы спрошены ровно раз |
| `ui-min-off-by-one` — минимум пароля 11 вместо 12 | проверялся только пароль из 5 символов | границы 11/12 и 128/129, в том числе в code points |
| `gen-always-gzip` — gzip без проверки выгоды | «несжимаемые» данные в тесте были периодическими | высокоэнтропийные байты остаются identity; половина нулей — gzip |

Четвёртая, `ui-overlap` (снята защита от повторного входа задачи в `run()`),
**эквивалентна**: следующий запуск планируется только после завершения
предыдущего, а обработчик видимости сам пропускает выполняющиеся задачи, так что
ветка недостижима. Итог: 23 пойманы, 1 эквивалентная.

### C (63)

Первый прогон: 55 пойманы, 5 выжили, 3 не собрались. Не собравшиеся
переформулированы так, чтобы ломать то же решение без предупреждений компилятора
(`-Werror`). Четыре выживших указали на пробелы в тестах; тесты добавлены, и
повторный прогон поймал все семь:

| Мутация | Пробел | Закрыт |
|---|---|---|
| `auth-token-prefix` — токен сравнивается по длине присланного | проверялся только укороченный токен | `test_tokens_with_anything_appended_are_refused` |
| `json-no-chars-max` — не проверяется максимум code points | длинные строки упирались раньше в размер буфера | `test_code_point_limit_is_checked_where_the_buffer_has_room`; в v1 — пароль на символ длиннее 128 |
| `api-no-idem-key` — маршрут с `IDEMPOTENT` принимает запрос без ключа | тест проверял только статус, а 422 даёт и другая ветка | сверяется поле ошибки `Idempotency-Key` |
| `http-query-in-path` — query остаётся частью пути при маршрутизации | в адаптере не было запроса с query | `test_query_is_not_part_of_the_path` на настоящем сервере |
| `auth-change-keeps-sessions` (переформулирована) | — | поймана |
| `json-segments-bytewise` (переформулирована) | — | поймана |
| `api-any-host` (переформулирована) | — | поймана |

Пятая выжившая, `writer-unclosed-ok` (из `web_json_writer_finish()` убраны
проверки `depth != 0` и `after_key`), **эквивалентна**: `has_value[0]`
выставляется только при закрытии значения верхнего уровня, поэтому незакрытый
контейнер уже даёт `!has_value[0]`, а ключ без значения возможен только внутри
незакрытого объекта. Оставшееся условие отвергает те же документы.
