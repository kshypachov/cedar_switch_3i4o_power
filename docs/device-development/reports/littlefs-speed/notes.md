# Скорость SPI NOR и LittleFS (2026-09-19)

Задача владельца: ускорить запись и чтение LittleFS; проверить, что шина SPI быстрая;
если мешают мелкие запросы — буферы LittleFS и другие способы; найти бенчмарки LittleFS.
Уточнения по ходу:
- «пока не добьёшься скорости чтения сырых байтов по SPI хотя бы 1 МБ/с — не переходи
  к тюнингу LittleFS»;
- SPI1 — только NOR и FRAM, настройки SPI1 менять можно;
- тщательно выбирать DMA для периферии;
- DCACHE1 в конечном варианте должен быть включён;
- дерево Zephyr не править: буферы в PSRAM из-за релокации — вернуть нужное в SRAM
  настройками проекта.

Стенд: тестовая плата `.21` (ST-Link), прошивка через `west flash`, версия растёт с
каждой прошивкой (1.1.3+N). Замеры — шелл-командой `lfsbench` (src/diagnostic/lfs_bench.c),
настройки — `storage_bench`.

## 1. Шина быстрая, медленный драйвер

SPI1: ядро 160 МГц, `MBR=0` (÷2) → 80 МГц, NOR с `use-fast-read`. Теоретически ~10 МБ/с
на одну линию. В режиме опроса (`st,fifo-threshold` по умолчанию 1) сырое чтение —
240 КБ/с независимо от размера куска (256 Б, 4 КиБ, 32 КиБ): ~660 тактов на байт в
драйвере `spi_stm32`, а не в числе запросов.

| Вариант | 256 Б | 4 КиБ | 32 КиБ |
|---|---|---|---|
| Опрос, порог FIFO 1 (было) | 203 КБ/с | 239 КБ/с | 241 КБ/с |
| Опрос, `st,fifo-threshold = <8>` | 555 КБ/с | 834 КБ/с | 849 КБ/с |
| DMA, буфер в SRAM | 380 КБ/с | 3,6 МБ/с | 6,7 МБ/с |
| DMA, буфер в PSRAM (без DCACHE) | 451 КБ/с | 3,9 МБ/с | **таймаут (-11)** |

Данные сверены по CRC32 одинакового содержимого раздела между режимами.

## 2. DMA и кеши

- SPI1 обслуживает только GPDMA1: запросы `LL_GPDMA1_REQUEST_SPI1_RX = 6`,
  `SPI1_TX = 7`; у LPDMA1 из SPI только SPI3. Каналы 10 и 11 — линейные (0–11, FIFO
  8 байт; 12–15 — 2D, FIFO 32 байта), больше никем не заняты.
- DCACHE1 (ST, «STM32U5 DCACHE», слайд 2): стоит на S-AHB и кеширует **только внешнюю
  память** (OCTOSPI1/2, HSPI, FMC); запросы к SRAM и периферии идут в обход. Код,
  исполняемый через ремап ICACHE (`0x02…` → OCTOSPI1), идёт по C-AHB — DCACHE1 его не
  касается. DMA-мастера через DCACHE1 не ходят: при включённом DCACHE1 DMA во внешнюю
  память требует clean/invalidate, в SRAM — ничего.
- До 1.1.3+9 DCACHE1 был **выключен**: `DCACHE1_CR = 0x300` (EN = 0) на плате; Zephyr на
  U5 включает только ICACHE (soc/st/stm32/stm32u5x/soc.c). `CONFIG_DCACHE=y` давал только
  API и проверку в драйвере SPI. Включён с 1.1.3+9 (§6).
- `spi_stm32` при `CONFIG_DCACHE=y` принимает для DMA только буферы в SRAM образа
  (`soc/st/stm32/common/stm32_cache.c`, `stm32_buf_in_nocache`), остальное — `-ENOTSUP`.
- DMA в PSRAM ненадёжен и без кеша (32 КиБ — таймаут).

Итог: DMA только с буферами в SRAM. А в PSRAM (релокация `app`, `subsys__fs` и др.) —
стеки потоков приложения, кеши LittleFS, буферы ZMS и хранилища образа; `spi_nor` кладёт
байты команды на стек вызывающего (`uint8_t buf[6]`, spi_nor.c:403), LittleFS читает
большие выровненные куски прямо в буфер вызывающего (`lfs_bd_read`, «bypass cache»),
ZMS — в буферы и структуры на стеке вызывающего. Переносить в SRAM всех, кто ходит во
флеш, — почти всё приложение.

### Сверка с ST AN5593 (GPDMA, rev 9) по регистрам каналов на плате

| | AN5593 (SPI — табл. 24, общие правила — 2.2–2.4) | У нас (GPDMA1 CxCR/CxTR1/CxTR2) |
|---|---|---|
| Запросы | SPI1_RX 6, SPI1_TX 7 | REQSEL 6 / 7 ✓ |
| Канал | линейный, FIFO 2 слова (0–11) | 10, 11 ✓ |
| Порт периферии | 0 (прямой путь к APB1/APB2) | SAP/DAP = 0 ✓ |
| Порт памяти | 1 (SRAM1 — ведомый по умолчанию порта 1) | тоже 0 — драйвер `dma_stm32u5` на U5 порты не задаёт |
| Ширина на стороне SPI | 32 бита (SPI упаковывает кадры) | 8 бит — `spi_stm32` берёт ширину по размеру кадра |
| Приоритет | 1–2 для периферии | был 0; с 1.1.3+15 — 2 (`STM32_DMA_PRIORITY_HIGH` в overlay) |

Два отклонения — в драйверах Zephyr, стоят только тактов шины (других DMA-мастеров
нет), на корректность не влияют. Исправление — правка дерева Zephyr, не делалась.

## 3. Решение: прослойка в SRAM (modules/flash-sram-proxy)

Устройство `cedar,flash-sram-proxy` поверх `spi_flash`: каждая операция выполняется в
своём потоке (стек в SRAM) через свой буфер 4 КиБ в SRAM; разделы NOR (`storage_zms`,
`slot1`, `storage`, `scratch`) перенесены под прослойку в overlay приложения с теми же
адресами и метками. Отдельная библиотека модуля не релоцируется — `bounce`,
`proxy_stack`, `proxy_data` по адресам `0x2001…`/`0x2004…` (проверено `nm`). MCUboot
собирается без overlay приложения и ходит в `spi_flash` напрямую. Дерево Zephyr не
менялось. Плюс код `spi_stm32.c`, `dma_stm32u5.c`, `spi_nor.c` — в SRAM
(`zephyr_code_relocate … RAM_TEXT`): мелкая операция 0,83 → 0,32 мс.

## 4. Результат: тот же код с DMA и без (1.1.3+8 против 1.1.3+7)

| Замер | Без DMA | DMA + прослойка + код в SRAM |
|---|---|---|
| Сырое чтение 16 Б, на операцию | 388 мкс | 304 мкс |
| Сырое чтение 256 Б | 137 КБ/с | 826 КБ/с |
| Сырое чтение 4 КиБ | 204 КБ/с | **3,77 МБ/с** |
| Сырое чтение 32 КиБ | 205 КБ/с | **4,97 МБ/с** |
| Программирование 4 КиБ | 139 КБ/с | 348 КБ/с |
| Стирание 4 КиБ (микросхема) | 80,5 КБ/с | 80,8 КБ/с |
| Стирание + программирование | 51 КБ/с | 65,5 КБ/с |
| Проверка записи чтением, 32 сектора | 0 ошибок | 0 ошибок |
| LittleFS: запись файла 128 КиБ | 35,4 КБ/с | 55,5 КБ/с |
| LittleFS: чтение файла | 141 КБ/с | 779 КБ/с |
| Сохранение метаданных (tmp + sync + rename), среднее / худшее | 304 / 809 мс | 88 / 289 мс |

микросхемы (~45 мс на сектор 4 КиБ).

## 5. Бенчмарки LittleFS из открытых источников (ориентир)

Сводка поиска (агент, 2026-09-19): опубликованные скорости записи LittleFS на NOR —
25–75 КБ/с (ESP32 внутренняя флешь 53–73 КБ/с, EFM32 + W25Q128JV ~27 КБ/с,
RP2040 ~57 КБ/с), чтение — 70 КБ/с … 2,3 МБ/с (ESP32). Предел записи со стиранием для
W25Q128JV: 45 мс на сектор + 16 × 0,4 мс ≈ 79 КБ/с. LittleFS проверяет каждую запись
чтением обратно (`lfs_bd_flush(..., validate)`), поэтому быстрое чтение ускоряет и запись.
Источники: github.com/joltwallet/esp_littlefs (раздел Performance),
github.com/littlefs-project/littlefs issues 214, 535, 783, datasheet W25Q128JV.

Сверка данных между режимами: одно и то же содержимое раздела читается одинаково через
DMA (1.1.3+6) и опросом (1.1.3+7) — CRC32 1 МиБ `7c5420de` в обоих. Пары +8/+7 так
сравнивать нельзя: между ними бенчмарки файлов писали в раздел. Запись проверяется
чтением в `lfsbench rawwrite` (0 ошибок на 32 секторах в каждой сборке).

## 6. DCACHE1 включён (1.1.3+9)

Аудит перед включением: DMA в devicetree — только у SPI1 (узлы SAI выключены, у UART
`dmas` нет, SPI2 с W5500 и ESP32 — опросом); SPI1 через прослойку — только SRAM; память
PSRAM приложение не перенастраивает (окно memory-mapped поднимает MCUboot); драйвер
записи XIP-флеши инвалидирует DCACHE по записанному диапазону
(`flash_stm32_ospi_xip.c:535`). Включение — `sys_cache_data_invd_all()` +
`sys_cache_data_enable()` в `src/helpers/memory.c` (PRE_KERNEL_1). На плате
`DCACHE1_CR = 0x101` (EN = 1).

| Замер (DMA + прослойка) | DCACHE1 выкл (+8) | вкл (+9) |
|---|---|---|
| LittleFS: чтение файла | 779 КБ/с | 1,53 МБ/с |
| `statvfs` | 27 мс | 5,5 мс |
| Сохранение метаданных, среднее | 88 мс | 80 мс |
| Сырое чтение 4 КиБ | 3,77 МБ/с | 4,57 МБ/с |

Проверено на +9 и +12: `crash fault` → дамп `verified`; загрузка образа через веб по
Ethernet — **1,49 МБ за 143–152 с (9,5–10,3 КиБ/с), кусок p50 0,3 с, проверка образа
4 с** (было 620 с, 2,3 КиБ/с, кусок 1,5 с, проверка 71 с); `GET /` 200.

## 7. Тюнинг LittleFS

Разрешён после цели 1 МБ/с. Сравнения на `.21`, по 30 сохранений метаданных:

| Вариант | Сохранение метаданных (tmp + sync + close + rename) | «На месте» (sync + close, без tmp/rename) |
|---|---|---|
| cache-size 2048 (+10) | 83,5 мс (rename 75) | 19 мс |
| cache-size 4096 (+11) | 32 мс (rename 23) | 20 мс |
| cache-size 4096 (+12, +13, позже) | 64–72 мс (rename 18–22, sync 37) | 20 мс |

- **cache-size 4096** (= блок) — оставлен: rename стабильно в 3–4 раза быстрее; время
  sync меняется со состоянием ФС (2–40 мс). Запись/чтение файлов не изменились (запись
  упирается в стирание микросхемы ~45 мс на 4 КиБ: 60 КБ/с при пределе ~80).
  `FS_LITTLEFS_FC_HEAP_SIZE` 64 → 128 КиБ (PSRAM): кеш каждого открытого файла теперь
  4 КиБ, 32 файла по-прежнему помещаются.
- lookahead 256 → 512 — без эффекта (256 Б и так покрывают 2048 блоков из 1280).
- **Сохранение «на месте» в 3–4 раза быстрее tmp + rename** и так же устойчиво к пропаданию
  питания: LittleFS фиксирует файл атомарно на sync/close (README littlefs). Это правка
  `write_meta()` хранилища образа — не сделана, решение владельца (вместе с пакетной
  записью метаданных раз в 64 КиБ).

## Не сделано / открыто

- Ускорение записи дальше — только в обход стирания: заранее стирать (алгоритм
  владельца «стирать на кусок вперёд» — отложен) или блоки 64 КиБ (переформатирование,
  хуже для мелких файлов).
- FRAM на той же шине без прослойки: читать только из потока со стеком в SRAM в буфер
  в SRAM (сейчас это MAC, на main при загрузке); иначе драйвер SPI вернёт `-ENOTSUP`.
- Мелкая операция через DMA — ~0,3 мс (настройка DMA на два участка, прерывание,
  переключение на поток прослойки); ZMS читает записи по 16 Б, настройки при этом
  не медленнее опроса (132–150 мс против 164 мс на обход).
- Стек потока прослойки занят на 60 % (624 из 1024).
