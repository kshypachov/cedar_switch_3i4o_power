# Экран «Прошивка» (обновление STM32) — заметки фронтенда

Форк D, 2026-09-15. Контракт — `openapi.json` и `api-contract.md` «Обновление STM32»; mock — форк C
(`tools/api-contract/cedar_contract/mock/system.py`, `mcuboot.py`).

## Что сделано

- `src/api/system.ts` — `getSystemFirmware`, `startSystemUpdate`; типы `SystemFirmware`,
  `SystemUpdateSummary`, `SystemUpdateRequest` в `api/types.ts`. `createUpload` уже принимает
  `target` (тип из схемы); экран ESP32 его по-прежнему не шлёт.
- Маршрут `/firmware`, пункт меню «Прошивка», ссылка «Обновить» у версии STM32 на обзоре.
- `src/features/system-update`:
  - `version.ts` — разбор `major.minor.revision+build` и сравнение (build входит в порядок);
  - `install.ts` — `followSystemInstall` (задача до `rebooting`) и `waitForReboot` (ждёт смены
    `boot_id`), без React, на фейковом устройстве и часах;
  - `FirmwareCard.tsx` — работающая прошивка, подтверждение с локальным отсчётом между опросами,
    предупреждение о сбросе, `swap_pending`, итог последнего обновления;
  - `SystemUpdateScreen.tsx` — файл, SHA-256, загрузка с `target: "stm32u585"`, проверка,
    сравнение версий, флажок понижения, подтверждение, фазы, ожидание перезапуска.
- Общий код с экраном ESP32 переиспользован без смены поведения: `uploader.ts` как есть;
  `phases.ts` получил `phaseRowsOf(phases, job)` (у ESP32 `phaseRows` = частный случай);
  `remember.ts` получил `memoryAt(key)` — у STM32 свой ключ `cedar.system-update`.

## Решения экрана

- **Задача установки живёт до перезапуска.** Экран опрашивает её до `rebooting` (или конца), дальше
  опрашивает `/system/status` до смены `boot_id`. `boot_id` «до» — из самой задачи (`Job.boot_id`),
  запасной — из `SystemStatus` перед запросом. 404 задачи — устройство уже перезапустилось;
  после `requesting` три неотвеченных опроса подряд — тоже перезапуск.
- **401 после перезапуска** — сессии не пережили перезапуск: экран отправляет на вход с сообщением
  «Сессия завершена», путь остаётся `/firmware`, итог виден сразу после входа.
- **Ожидание** — до 180 с (обмен ~34 с, старт ~40 с по шагу 0), опрос раз в 2 с; по истечении —
  сообщение и кнопка «Ждать снова», без вывода о провале.
- **Понижение** — только флажком; `acknowledge_downgrade=true` уходит только при `older`.
  Та же версия — «переустановка» без флажка; несравнимые версии — «сравнить не удалось», без флажка
  (устройство само ответит 422, если сочтёт образ старше).
- **Подтверждение** — встроенная панель (не `<dialog>`: в jsdom он неполный), ничего не шлёт до
  второго нажатия.
- Загруженный образ ESP32 под ключом STM32 не принимается за свой (сообщение и забыть).

- **Панель подтверждения** закрывается сразу при отправке (второе нажатие не шлёт второй запрос) и
  сбрасывается, если очередной опрос показал, что установка больше не разрешена (прошивка не
  подтверждена, обмен уже запрошен — например, из другого браузера).

## Что проверяется только на устройстве

- строки `reason` (ниже) и `SystemStatus.firmware_version`/`running.version` в формате
  `major.minor.revision+build` — иначе сравнение покажет «сравнить не удалось»;
- настоящий перезапуск: сколько устройство молчит (ожидание — до 180 с), вход после него, 401;
- загрузка 1,4 МБ сразу во второй слот: скорость и продолжение после перезапуска посреди приёма;
- `device.spec.ts` экран «Прошивка» не открывает.

## Причины недоступности

Контракт не перечисляет `reason` для `SystemFirmware.update` и `features.stm32_update`. Mock (форк C)
выбрал `firmware_unconfirmed` и `update_running`; словарь знает их и `not_implemented`, неизвестная
строка показывается как есть. **Устройство должно отдавать те же строки** — иначе в интерфейсе
будет английский код.
