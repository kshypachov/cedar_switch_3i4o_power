# Веб-интерфейс отвечает 409 на всё, кроме API (2026-09-18)

## Симптом

Устройство 192.168.88.10 живо: ping, порт 80 и telnet (23) открыты.
`GET /`, `/index.html`, `/assets/...`, неизвестные `/api/v1/...` → голый
`HTTP/1.1 409 Conflict` без тела. Пути, у которых есть свой ресурс
(`/api/v1/auth/state`), → 200.

## Причина

1. Всё, что не API, обслуживает один динамический ресурс `fallback_detail`
   (`src/web/web_server.c:95`, передан в `HTTP_SERVICE_DEFINE` как `res_fallback`).
2. Zephyr сериализует динамический ресурс: при начале транзакции ставит
   `dynamic_detail->holder = client`, другому клиенту отвечает 409
   (`zephyr/subsys/net/lib/http/http_server_http1.c:775`). Снимается `holder`
   только в конце успешной транзакции (`http_server_http1.c:538`, `:629`) или при
   освобождении клиента.
3. Освобождение клиента (`client_release_resources`,
   `zephyr/subsys/net/lib/http/http_server_core.c:540`) обходит только
   `HTTP_SERVICE_FOREACH_RESOURCE` — зарегистрированные ресурсы. `res_fallback`
   в этот список не входит (он берётся отдельно, `http_server_core.c:1727`).
4. Итог: если транзакция на fallback оборвалась (браузер закрыл соединение
   посреди отдачи файла, ошибка отправки, таймаут неактивности, RST), клиент
   освобождается и слот обнуляется, а `fallback_detail.holder` остаётся
   указывать на слот `server_ctx.clients[k]`. Все следующие запросы в fallback
   из других слотов получают 409 — до перезагрузки или пока новый клиент
   случайно не займёт тот же слот и не завершит запрос в fallback.

Подтверждение на плате: `net conn` в telnet-шелле — на порту 80 нет ни одного
TCP-соединения (только слушающий `[::]:80`), а 409 сохраняется. Зависшего
клиента нет — блокировка утекла.

Прямое подтверждение через `devmem` (адреса из ELF `build/`, раскладка PSRAM
та же — `fallback_detail.cb` читается как `web_callback`|1 = 0x0200a2ed):

| что | адрес | значение |
|---|---|---|
| `fallback_detail.holder` | 0x700009b0 | 0x7000c470 = `server_ctx.clients[3]` |
| `web_api_00_auth_state_detail.holder` | 0x700009d8 | 0 |
| `clients[0..3].fd` | 0x7000a580 + k·0xa50 | 0xffffffff у всех четырёх |
| `clients[3].service` | 0x7000c474 | 0 (слот обнулён `memset`) |

То есть все четыре слота свободны, а блокировку держит освобождённый
`clients[3]`. Новый клиент занимает первый свободный слот, поэтому до
`clients[3]` дело доходит только при четырёх одновременных соединениях —
в обычной работе блокировка сама не снимется. Случилось это, когда браузер
держал четыре параллельных соединения и одно из них оборвалось посреди ответа
fallback.

## Когда появилось

- **Zephyr:** `res_fallback` добавлен в `ea6ca4e8b74` (2025-01-10, «net: http_server:
  allow specifying a fallback resource»). `client_release_resources` при этом не
  изменили: последняя содержательная правка — `ddaeb1379a0` (2024-11-29), после —
  только переименование статуса (`43d3387634e`, 2026-01-09). Ошибка есть с самого
  появления fallback — это не регрессия Zephyr. Коммит Matt Rodgers, написан
  2025-01-10, влит 2025-01-28, первый релиз с ним — **v4.1.0**. На момент коммита
  `holder` и `client_release_resources` уже были (с `4b157b90997`, 2024), коммит
  добавил новый путь к динамическому ресурсу мимо обхода освобождения. В нашем
  дереве исправления нет.
- **Апстрим на 2026-09-18:** не исправлено. `client_release_resources` в main
  (последний коммит файла `b5f5f9ad2e9`, 2026-09-08) такая же, `res_fallback`
  по-прежнему берётся только в поиске ресурса. PR, добавивший fallback, —
  zephyrproject-rtos/zephyr#83811. Поиск по issues/PR (fallback, holder, 409,
  TRANSACTION_ABORTED) ничего не нашёл; открытые PR по `net: http`
  (#118586, #116776, бэкпорты) освобождение не трогают.
- **У нас:** регрессия пришла с `9dc8600` (2026-09-13, P2, «Serve API v1 and the
  browser application, and remove the legacy web server»), в нём появился
  `src/web/web_server.c`. До него файлы интерфейса были статическими ресурсами
  (`HTTP_RESOURCE_TYPE_STATIC`, генерируемый `web_resources.inc`), блокировки у них
  нет. Динамический fallback был и раньше (`fallback_redirect_handler` в
  `http_server_init.c`), но отдавал только 302 без тела на неизвестные URL — его
  залипание ломало лишь редирект. С `9dc8600` через динамический fallback пошли
  все файлы интерфейса, и та же ошибка Zephyr стала выключать весь веб.
  Последующие коммиты файла (`4c6e4d3`, `66f7326`) fallback не трогали.

## Закрывает ли прошивка зависшие соединения

Да, этот механизм есть и работает:

- `CONFIG_HTTP_SERVER_CLIENT_INACTIVITY_TIMEOUT=10` (по умолчанию, в `prj.conf`
  не задан): через 10 с без активности `client_timeout` делает
  `shutdown(SHUT_RD)`, poll видит это, клиент закрывается
  (`http_server_core.c:673`).
- TCP: `NET_TCP_RETRY_COUNT=9`, `NET_TCP_INIT_RETRANSMISSION_TIMEOUT=200` —
  пропавший посреди отправки пир сбрасывается стеком. `NET_TCP_KEEPALIVE`
  выключен; при таймауте неактивности HTTP он не нужен.
- `CONFIG_HTTP_SERVER_MAX_CLIENTS=4`.

Проблема не в том, что соединения не закрываются, а в том, что закрытие
соединения посреди запроса в fallback не снимает блокировку fallback. Штатное
закрытие как раз и оставляет утёкший `holder`.

## Патч Zephyr (2026-09-18, по решению владельца)

`patches/zephyr/http_server-release-fallback-resource-on-client-close.patch`,
запись в `patches/patches.yml`, строка в `patches/README.md`.

- `client_release_resources` вынесена в `client_release_resource(client, detail)`
  и вызывается для каждого ресурса сервиса и для `service->res_fallback`.
- Тест `test_http1_fallback_released_on_abort` в
  `zephyr/tests/net/lib/http_server/core`: отдельный сервис на 8081 только с
  динамическим fallback (основной сервис оставлен без fallback — HTTP/2-тест
  ждёт 404 на `/index.html`); половина тела POST держит fallback, соединение
  закрывается, ждём `TRANSACTION_ABORTED`, затем второй клиент получает 200.
- Прогон в контейнере `tests/ci` (`native_sim/native/64`, twister):
  с патчем `net.http.server.core` 73/73; без правки ядра новый тест падает,
  остальные 72 проходят; `cedar.web_api_http` с патчем 22/22.
  `checkpatch.pl`: 0 ошибок, 0 предупреждений.
- Круговой прогон по README: откат, `west patch apply` одной записью, diff
  совпал с проверенным. **В общее дерево не наложен** — снят обратно; наложить
  одной записью, как в `patches/README.md`.
- На плате не проверено: прошивку с патчем не собирали (в этом окружении нет
  `zap-cli`).

## Установка на плату 192.168.88.10 (2026-09-18, по просьбе владельца)

- Патч наложен в общее дерево одной записью (`west patch apply`), прошивка
  собрана в `build/`: 48 ячеек PSA (`global_data` 0x1c204), PKA для PSA выключен,
  `client_release_resource` в образе. `zephyr.signed.bin` sha256 `b3b010b4…`,
  1 448 116 Б, в слоте — hash `21016ff0…`.
- Сборку сначала ломал `src/diagnostic/diag_report.c`: владелец включил
  `NET_STATISTICS_PER_INTERFACE`, а неиспользуемая `iface_cb` вызывает
  закомментированную `print_stats`. `iface_cb` закомментирована так же, как
  код вокруг.
- Загрузка через API v1 (скрипт — копия `stm32-update/hw/web_update_a.py`
  с докачкой и паузой). Два зависания с IWDG (`reset cause 0x11`) на
  262 144 и 311 296 Б — запись во флеш при XIP, известная проблема; вторая
  загрузка докачана с `received_bytes`, 4,0 КиБ/с, verify 103 с.
- Установка: 17 с до перезагрузки, ответ через 66 с. Новый образ работает,
  `awaiting_confirmation`, самоподтверждение через 20 мин. Прошлая установка
  1.1.1 (job_0000001c, образ с 48 ячейками) откатилась именно так —
  `boot_changed`, сброс до подтверждения; поэтому на плате и оставалось 16.
- Сразу после загрузки `/` и `/index.html` отвечают 200.
- Ячейки PSA на плате после установки (21:46, boot `boot_0db403259a65ad67`,
  аптайм ~4,5 мин), `devmem` по `global_data` 0x200238dc, шаг 2400 Б:
  флаг `key_slots_initialized` на смещении 115 200 (48 × 2400, 0x2003fadc) = 1,
  на смещении 38 400 (где он лежал в образе с 16 ячейками) = 0; ячейки 1–4 —
  AES-CCM сессионные ключи (state 2), 0 и 5–47 пустые (нули). В старом образе
  с 38 400 шли таблицы AES и заливка стека 0xaa. **Массив на 48 ячеек.**
- Самоподтверждение прошло: 22:01:46, `confirmed: true`, `last_update`
  succeeded, аптайм 1 207 с без перезагрузок.
  Внимание: `build/` пересобран в 21:40 (CLion?, sha256 `367f1ee3…` ≠
  прошитого `b3b010b4…`); адрес и размер `global_data` в нём те же.

### Пропала вкладка «Прошивка» (22:20) и вторая установка

- Причина — встроенный фронтенд: `src/web/frontend/dist` в основной рабочей
  копии был собран 2026-09-15 11:15 (`0.1.0+df852ea3a0fa-dirty`), до коммита
  `af0d9ca` «Add the Firmware screen» (09-15 20:14); в его JS нет
  `system/updates`. Прежний образ на плате собирался в `cedar_p7`, где `dist`
  от 17:59 с экраном. Сборка прошивки npm не запускает и берёт что лежит в `dist`.
- Фронтенд пересобран из main (`SKIP_E2E=1 tests/ci/run-frontend-tests.sh`:
  26 файлов, 455 тестов, 113 650 Б gzip), версия `0.1.0+9a75d2e6f023-dirty`
  (`-dirty` — незакоммиченные правки вне фронтенда).
- `build/` в это время трогала другая сессия (cmake-4.2.3, отчёт
  `cmake-relocation-errors`): сборка в нём упала на `ar: file format not
  recognized`. Прошивка собрана с нуля в отдельном каталоге с
  `ZAP_INSTALL_PATH=modules/lib/matter/.environment/cipd/packages/zap`
  (Rosetta уже работает): sha256 `41df4595…`, 1 454 192 Б, 48 ячеек, PKA выкл.,
  патч HTTP в образе.

## Варианты исправления (не сделано, решение владельца)

- Патч Zephyr в `patches/`: в `client_release_resources` дополнительно
  проверять `service->res_fallback` (если он динамический и `holder == client`,
  снять и вызвать `HTTP_SERVER_TRANSACTION_ABORTED`). Это же стоит отправить
  апстрим.
- Только в приложении: вместо `res_fallback` зарегистрировать обычный ресурс
  с шаблоном `/*` (последним по имени, т.к. wildcard-и перебираются в порядке
  имён) — тогда он попадёт в `HTTP_SERVICE_FOREACH_RESOURCE` и будет
  освобождаться.

## Matter на той же плате: CASE падает с PSA -141 (2026-09-18)

Плата работает 25 ч без перезагрузки (`kernel uptime` 90 556 с), прошивка 1.1.1,
3 fabric, окно ввода в сеть закрыто. Каждая попытка контроллера подключиться
заканчивается так:

```
[SC]Sent Sigma2Resume msg
[SC]Success status report received. Session was established
<err> [CR]PSA error: -141
<err> [IN]CASE Session establishment failed: ac
<err> [IN]Data received on an unknown session (LSID=...). Dropping it!
```

-141 — это `PSA_ERROR_INSUFFICIENT_MEMORY`: нет свободной ячейки ключа PSA.

**На плате прошивка с 16 ячейками, а не с 48.** Массив ячеек
(`global_data` из `psa_crypto_slot_management.c`, адрес 0x2002394c, одна ячейка
2400 Б) прочитан через `devmem` в telnet-шелле:

- ячейки 1–14 заняты: тип 0x2400 (AES), 128 бит, использование 0x302,
  алгоритм 0x05488100 (AES-CCM), id 0x40000001…0x4000000e, state 2 (FULL),
  readers 0. Это 7 сессий Matter по два ключа (i2r и r2i);
- ячейки 0 и 15 пустые;
- на месте «ячейки 16» (смещение 38 400) лежит `0x1` — это флаг
  `key_slots_initialized` 16-ячеечного массива; дальше таблицы AES
  (0x01 0x02 0x08 0x10 0x20…, T-таблицы) и заливка стека 0xaaaaaaaa.
  В сборке с 48 ячейками там были бы ячейки.

Сборка `build/` от 17.09 18:53 содержит 48 ячеек (`global_data` 0x1c204 =
115 204 Б) и совпадает с платой по адресам всех 9 точек входа потоков, но
число ячеек не меняет раскладку кода, поэтому это совпадение ничего не
доказывает. На плату эта сборка не прошита (или прошит другой образ).

Две свободные ячейки при 14 занятых, по-видимому, не хватает на возобновление
сессии: вместе с двумя сессионными ключами нужен как минимум ещё один
временный ключ. Сколько именно нужно — не проверено.

Аппаратный PKA к этому отношения не имеет: он не хранит ключи в ячейках. По
решению владельца PKA всё равно выключен в `prj.conf` 2026-09-18
(`CONFIG_PSA_CRYPTO_DRIVER_STM32_PKA=n`, `CONFIG_STM32_PKA_ECP_P256=n`,
p256-m остаётся). Сам -141 это не исправит. Нужна прошивка с
`CONFIG_MBEDTLS_PSA_KEY_SLOT_COUNT=48`, эта строка уже есть в `prj.conf`.

Веб (409) и Matter (-141) — две независимые ошибки, обе проявились после
~суток работы.

## Не проверено

- Какое именно событие оборвало транзакцию на этой плате (логов на момент сбоя
  нет).
- Проверка «снятием» блокировки: открыть 4 параллельных keep-alive соединения
  и в каждом сделать `GET /` — клиент, попавший в утёкший слот, завершит
  запрос и обнулит `holder`. Не делал, чтобы не потерять состояние платы.
