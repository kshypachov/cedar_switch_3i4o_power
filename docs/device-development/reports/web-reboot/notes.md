# Перезагрузки при открытом веб-интерфейсе — разбор 2026-09-17

Сообщение владельца: «в модуле веб-интерфейса похоже есть утечка памяти; устройство падает спустя
какое-то время, если я открываю веб-интерфейс, и не падает вовсе, если интерфейс не открыт».

Уточнения владельца (2026-09-17):

- падение выглядит как **перезагрузка**; консоль в этот момент не подключена, дампа нет;
- сеть — **Wi-Fi через ESP32-C6 (esp_hosted_mcu)**, не Ethernet;
- страница интерфейса значения не имеет, падает при любой.

Статус: **причина не установлена**. Разбор пока только по коду; ниже — главный вывод о том, почему
падение невидимо, отрицательные результаты поиска утечки и план измерения.

## Главное: любой fatal error на этой плате выглядит как молчаливая перезагрузка

В сборке (`build/cedar_switch_3in4out_power/zephyr/.config`):

    # CONFIG_RESET_ON_FATAL_ERROR is not set
    CONFIG_FAULT_DUMP=2
    CONFIG_HW_STACK_PROTECTION=y
    CONFIG_APP_IWDG=y
    CONFIG_APP_IWDG_TIMEOUT_MS=20000

`zephyr/kernel/fatal.c:38-50`: без `CONFIG_RESET_ON_FATAL_ERROR` штатный
`k_sys_fatal_error_handler()` зовёт `arch_system_halt()` — процессор встаёт со снятыми прерываниями.
Сторож IWDG кормит отдельный поток `app_iwdg` (`src/services/system/system_service.c:126-166`,
`K_PRIO_COOP(0)`, `k_msleep(timeout/4)`), и после остановки он больше не работает → через ≤20 с
IWDG перезагружает SoC.

Отсюда: **перезагрузка без консоли не отличает** bus fault, MPU fault (переполнение стека),
ASSERT и настоящий залипон (livelock/голодание кооперативного потока). Дамп `FAULT_DUMP=2` с именем
потока (`CONFIG_THREAD_NAME=y`) печатается в консоль и там же теряется.

Причина перезагрузки записывается: `hwinfo_get_reset_cause()` снимается в `PRE_KERNEL_1`
(`system_service.c:71-79`) и печатается командой `sysupd status`. При остановке после fault причина
будет **watchdog** — та же, что и при залипоне.

## Отрицательные результаты: динамической памяти в веб-пути нет

Поиск `malloc|calloc|realloc|strdup|k_malloc|k_heap_alloc|net_buf_alloc|k_mem_slab_alloc|fs_open`:

- `modules/web-api/lib`, `modules/web-auth/lib`, `modules/web-assets/lib`, `src/web/**` — **ни одного
  вызова**. Слоты запросов статические: `struct slot slots[CONFIG_HTTP_SERVER_MAX_CLIENTS]`
  (`modules/web-api/lib/web_api_http.c:42-56`), освобождение по
  `HTTP_SERVER_TRANSACTION_ABORTED|COMPLETE` (там же, строки 357-361).
- `src/services/**`, `modules/job-manager`, `modules/log-store`, `modules/network-manager`,
  `modules/matter-service`, `modules/coprocessor-manager`, `modules/settings-registry` — только два
  парных `fs_open()` в журналах обновления, не в пути опроса.
- драйверы Wi-Fi: `zephyr/drivers/wifi/esp_hosted_mcu/esp_hosted_mcu.c` — единственное выделение
  `net_pkt_rx_alloc_with_buffer(..., K_NO_WAIT)` с корректным `net_pkt_unref()` на обеих ветках
  ошибки (строки 205-218); `zephyr/drivers/misc/esp_hosted_mcu/*.c` (SPI-транспорт) — выделений нет,
  буферы статические (`SPI_STASH_DEPTH`, `TX_AGG_SIZE`).
- переполнение слотов HTTP-сервера обработано: при `num_clients >= concurrent` слушающий fd
  снимается с опроса (`zephyr/subsys/net/lib/http/http_server_core.c:1091-1093`), лишнее соединение
  закрывается (там же, 1154-1155).

То есть утечка кучи в коде веб-модулей не подтверждается. Остаются пулы сети (`net_pkt`/`net_buf`),
контексты TCP, стеки потоков и арена libc (её использует Matter) — это измеряется, см. ниже.

## Что опрашивает браузер (нагрузка, которой нет при закрытом интерфейсе)

Один планировщик, запросы не накладываются друг на друга, в фоновой вкладке интервал растягивается
до 5 с (`src/web/frontend/src/state/scheduler.ts`).

| Страница | Эндпоинты | Интервал |
|---|---|---|
| Обзор | `system/status`, `network/status`, `matter/status`, `coprocessor/status` | 5 с (coprocessor 10 с) |
| Сеть | `network/status`, `network/config`, транзакция | 5 с / 1 с |
| Matter | `matter/status`, окно ввода, фабрики | 5 с / 2 с |
| Логи | записи, источники, `coprocessor/status` | 1 с / 5 с |
| Обновление | `system/firmware`, `capabilities`, job | 2 с / 0,5 с |

Браузер держит до 6 параллельных соединений, у сервера 4 слота (`CONFIG_HTTP_SERVER_MAX_CLIENTS=4`).

## План измерения

**Шелл доступен по сети:** `CONFIG_SHELL_BACKEND_TELNET=y`, `CONFIG_SHELL_TELNET_PORT=23` —
`telnet <ip> 23`, пересборка не нужна. Оговорка: telnet идёт по тому же TCP/Wi-Fi, при залипоне сети
умрёт вместе с ней; ценен сам тренд до смерти.

1. **Сразу после очередной перезагрузки:** `sysupd status` — причина сброса и счётчик кормлений IWDG.
2. **Пока страница открыта, раз в несколько минут:** `kernel stacks` (пиковые метки; смотреть
   `http_server` при 6144 Б и потоки esp_hosted), `kernel threads`, `net conn`, `net sockets`,
   `coproc logs`. Монотонный рост одного из чисел — это и есть утечка; если ни одно не растёт, а
   плата всё равно падает, утечки нет.
3. **Консоль с записью в файл** (`tio -l -o crash.log <порт>` или `screen -L`) и воспроизведение —
   единственный способ увидеть `FAULT_DUMP` с типом исключения, PC/LR, MMFAR/BFAR и **именем потока**.
   Имя потока определяет всё дальнейшее расследование.
4. **Разделить причину без браузера** (скрипты `tests/bench`): (а) только `ping`/трафик — драйвер;
   (б) цикл `curl` с keep-alive по одному эндпоинту — обработчик; (в) цикл `curl` с новым соединением
   каждый раз — оборот соединений и 4 слота.

### Если консоль держать подключённой нельзя

Добавить в `src/diagnostic/` свой `k_sys_fatal_error_handler()`: записать причину, PC, LR, MMFAR/BFAR,
имя потока и uptime, затем `sys_reboot(SYS_REBOOT_WARM)` вместо остановки; печатать запись при
следующем старте и в `sysupd status`. Побочная польза: после этого перезагрузка с причиной
**watchdog** будет означать именно залипон, а не fault.

Куда писать: **BBRAM (backup-регистры RTC)** — узел есть в DT
(`zephyr/boards/arm/cedar_switch_3in4out_power_rev3/cedar_switch_3in4out_power_rev3-common.dts:183-185`,
`st,stm32-bbram`, 32 регистра = 128 Б), `CONFIG_BBRAM_STM32=y` уже включён; смещение 0 занято
4-байтовым признаком подтверждения образа (`src/app-firmware-updater/firmware_updater.c:230-262`),
запись класть со смещения 8. `__noinit` в этом приложении опасен: часть данных релоцируется в PSRAM,
которую готовит MCUboot.

## Открытые вопросы

- Падает ли плата, если открыт **только экран входа** (сессии нет)? Если да — из подозреваемых
  уходят все постраничные обработчики, остаются опрос `auth/state`, отдача статики и оборот соединений.
- Сколько времени проходит до падения (минуты или часы) и повторяется ли оно с постоянным интервалом.

## Лог владельца 2026-09-17: ячейки ключей PSA кончаются, Matter больше не поднимает CASE

Файл `cedar-logs.txt` — выгрузка из log-store (`boot_1f064b3333ef5c41`, снимок с ~835 с по ~1601 с
аптайма, перезагрузки в нём нет). 1929 строк info, 71 error, 0 warn.

Ключевая последовательность, повторяется 7 раз начиная с 1408918 мс (≈23,5 мин аптайма):

    1408711 [SC]Success status report received. Session was established
    1408918 error [CR]PSA error: -141
    1408919 error [IN]CASE Session establishment failed: ac
    1409253 error [IN]Data received on an unknown session (LSID=35281). Dropping it!

`-141` — это `PSA_ERROR_INSUFFICIENT_MEMORY`
(`modules/crypto/tf-psa-crypto/include/psa/crypto_values.h:144`). Печатает его `LogPsaError()`
(`modules/lib/matter/src/crypto/CHIPCryptoPALPSA.cpp:491-497`) из пути вывода сессионных ключей.
**После первой такой ошибки ни одна CASE-сессия больше не устанавливается** — до конца выгрузки
(≈3 минуты) все попытки падают одинаково. Контроллер продолжает слать данные в сессию, которой у нас
нет, отсюда поток `Data received on an unknown session`.

### Почему кончаются ячейки

- `CONFIG_MBEDTLS_PSA_KEY_SLOT_COUNT=16` — это **значение по умолчанию Zephyr**
  (`zephyr/modules/mbedtls/Kconfig.tf-psa-crypto:416-418`), в нашем `prj.conf` оно не задавалось.
- Каждая живая защищённая сессия держит **две** ячейки: `CryptoContext::mEncryptionKey` и
  `mDecryptionKey` (`modules/lib/matter/src/transport/CryptoContext.h:167-168`), которые
  `PSASessionKeystore::DeriveSessionKeys()` получает двумя вызовами
  `psa_key_derivation_output_key()` (`src/crypto/PSASessionKeystore.cpp`). Ключи живут, пока жива
  сессия.
- Пул сессий здесь **17**: `CHIP_CONFIG_SECURE_SESSION_POOL_SIZE = CHIP_CONFIG_MAX_FABRICS * 3 + 2`
  (`src/lib/core/CHIPConfig.h:819`), а `CHIP_CONFIG_MAX_FABRICS` на Zephyr равен 5
  (`src/platform/Zephyr/CHIPPlatformConfig.h:89-90`). То есть только под сессии нужно до **34**
  ячеек при доступных 16.
- Постоянных потребителей ячеек, кроме сессий, здесь нет — проверено:
  - групповые ключи не используются: в логе **ноль** строк со словом «group»
    (`GroupKeyContext` создаётся только по `GetKeyContext`, не при старте);
  - операционные ключи фабрик не стоят в ячейках: `PSAOperationalKeystore` в
    `src/matter/matter_init.cpp:45` **закомментирован**, работает штатный
    `PersistentStorageOperationalKeystore` (`Server.h:297-299`), который держит ключ в хранилище
    и импортирует его на время подписи.
  Остаются временные ключи на время рукопожатия.

Арифметика не сходится независимо от того, есть ли вдобавок утечка: 16 ячеек не покрывают
сконфигурированный пул. В окне выгрузки на момент отказа видны сессии LSID 35275, 35278, 35279,
35280 — это 4 × 2 = 8 ячеек. Остальные 8 приходятся на сессии, установленные **до** начала снимка:
кольцо покрывает только последние ~13 минут из 23 минут аптайма, а сессии Apple Home (в логе две
фабрики, 4145 и 2C99) живут долго, пока держатся подписки. Восьми живых сессий достаточно, чтобы
выбрать все 16 ячеек, и никакой утечки для этого не требуется.

### Что изменено

`prj.conf`: `CONFIG_MBEDTLS_PSA_KEY_SLOT_COUNT=48` с пояснением.

Цена, **замерено на пересборке 2026-09-17** (не оценка): ячейки статические
(`MBEDTLS_PSA_STATIC_KEY_SLOTS=y` включается сам, раз `MBEDTLS_ENABLE_HEAP` выключен), размер ячейки
считается по самому большому включённому типу ключа — ~2,4 КБ из-за включённых RSA-типов.
`.bss.global_data` из `psa_crypto_slot_management.c`: было `0x9604` = 38 404 Б (16 ячеек), стало
`0x1c204` = **115 204 Б** (48 ячеек). Массив лежит **в SRAM**, а не в PSRAM: `libtfpsacrypto.a`
оставлена в SRAM намеренно (`CMakeLists.txt:294`, «горячие при сопряжении»). После сборки
`_end = 0x200541e8`, то есть статики в SRAM 336 КБ и арена malloc **431 КБ** из 768 КБ.

Если арены окажется мало (её пик так и не измерен), дешевле не резать число ячеек, а поставить
`CONFIG_MBEDTLS_PSA_STATIC_KEY_SLOTS=n`: тогда ячейка ~40 Б, а материал ключа (AES-128 — 16 Б)
берётся из кучи по факту использования — вместо 115 КБ статики получится ~2 КБ плюс единицы КБ в куче.

Проверка после перепрошивки: `[CR]PSA error: -141` должен исчезнуть. **Если он вернётся — значит
поверх нехватки есть настоящая утечка ячеек**, и тогда её надо искать отдельно (кандидаты: сессии,
которые освобождаются без `DestroyKey`, и групповые ключи).

Дешевле по памяти был бы вариант `CONFIG_MBEDTLS_PSA_STATIC_KEY_SLOTS=n` (тогда ячейка ~40 Б, а
материал ключа берётся из кучи libc), но он вносит выделения в криптопуть — не трогали.

### Связь с перезагрузками

Прямой связи пока нет: в этой выгрузке перезагрузки нет, а веб-интерфейс ничего в PSA не занимает
(`modules/web-auth/lib/web_auth_psa.c` использует только PBKDF2 и закрывает операцию). Правдоподобная,
но **не проверенная** цепочка: трафик открытого веб-интерфейса нагружает Wi-Fi и общий SPI, отсюда
всплеск повторов Matter (в логе их много перед отказом) и учащённая пересборка сессий, то есть
быстрее упираемся в потолок ячеек. Чтобы связать это с перезагрузкой, всё равно нужен дамп fault.
